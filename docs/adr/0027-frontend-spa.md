# ADR: Фронтенд - самостоятельное SPA

- Статус: Принято
- Дата: 2026-08-11
- Контекст: монорепозиторий DotnetVue3TemplateRu, `apps/frontend/web`, `libs/frontend/api-client`

## Контекст

Продукт - веб-сервис, в который пользователь заходит по своему адресу и работает целиком внутри него: списки, карточки записей, сводные экраны, история изменений. Встраивать этот интерфейс некуда - унаследованной системы, внутрь окна которой его нужно поместить, у продукта нет. Значит, фронтенду принадлежит вся вкладка: адресная строка, история навигации, глобальное состояние сессии.

Из этого сразу следуют требования, которых у встраиваемого кода не бывает.

Адрес экрана должен быть ссылкой, которую можно переслать коллеге и положить в закладку: человек шлёт ссылку на конкретную карточку, а не описывает словами, куда кликать. Кнопка "назад" в браузере обязана работать - иначе возврат из карточки к списку ломает привычный жест. И приложение само решает, что показать неаутентифицированному пользователю: увести его на вход к провайдеру и вернуть обратно после входа (ADR-0023) можно только владея адресной строкой, потому что authorization code возвращается именно через redirect на неё.

## Решение

**Фронтенд - одно SPA на Vue 3 в `apps/frontend/web`, собираемое Vite в обычное приложение (`index.html` + `main.ts`), без library mode.**

- Единственный composition root - `src/main.ts`: один `createApp(App)`, один экземпляр Pinia, один `QueryClient` (ADR-0029), один роутер, один экземпляр i18n, один OIDC-клиент. Изолировать нечего: приложение на странице одно.
- Маршрутизация - `createWebHistory(import.meta.env.BASE_URL)`: адрес экрана виден в адресной строке и работает как ссылка. Сервер обязан отдавать `index.html` на любой путь (SPA-fallback в `nginx.conf`), иначе перезагрузка страницы на вложенном маршруте даст 404.
- Сборка отдаёт один набор статики. Форматов ES и UMD, внешних синглтонов и глобальных переменных хост-страницы нет.
- Адрес backend приходит переменной сборки `import.meta.env.VITE_API_BASE_URL`. В разработке её ставит Aspire из адреса ресурса API; в образе - шаг сборки. Пустое значение означает "тот же origin" - это рабочий режим за общим reverse proxy.
- Библиотечным остаётся только `libs/frontend/api-client`: сгенерированный Orval TS-клиент. Он библиотека не ради переиспользования интерфейса, а потому что генерируется из другого источника (OpenAPI) и имеет свой цикл жизни - его нельзя править руками, а всё остальное можно.
- Компонентная база - Element Plus напрямую, со своей темой в `core/theme/index.scss`. Промежуточного пакета-обёртки нет.

## Почему не альтернативы

**Библиотека виджетов с mount-функциями.** Окупается, когда куски интерфейса вставляют в чужую страницу и на одной странице их несколько: тогда нужны изолированный Vue-app на каждый mount, in-memory-роутер и стабильный контракт mount/unmount. Здесь чужой страницы нет, поэтому всё это - плата без покупки. Хуже того, она отнимает нужное: адреса экранов перестают быть ссылками, а вход по OIDC становится невозможным, потому что redirect и callback требуют владения адресной строкой.

**Микрофронтенды.** Дают независимый деплой частей интерфейса ценой отдельных бандлов, версионирования и рантайм-композиции. Команда одна, деплой один; независимость деплоя частей интерфейса никем не запрошена.

**SSR или Nuxt.** Серверный рендер окупается публичным контентом и поисковой выдачей. Сервис работает после входа, индексировать нечего, а SSR добавил бы Node-процесс в прод-контур рядом с .NET - вторую среду исполнения, которую надо развернуть, обновлять и мониторить.

**Свой пакет UI-компонентов поверх Element Plus.** Второго приложения, которое его потребляло бы, нет; общая тема закрывается одним SCSS-файлом. Пакет-обёртка окупается, когда компоненты делят между репозиториями, а не внутри одного.

## Плюсы

- Адрес экрана - обычная ссылка: карточку записи можно переслать, положить в закладку, открыть кнопкой "назад".
- Вход по OIDC работает штатно: redirect и callback идут через адресную строку, которой владеет приложение.
- Composition root один и явный: чтобы понять, какие плагины подключены, достаточно прочитать `main.ts`.
- Сборка проще на целый уровень: нет library mode, двух форматов вывода, списка external и подмены `process.env.NODE_ENV`.
- Конфигурация приходит стандартным для Vite способом (`import.meta.env`), а не через глобальные переменные, которые пришлось бы документировать как публичный контракт.

## Минусы

- Приложение владеет всей вкладкой: встроить его фрагмент в чужую страницу без переработки нельзя.
- SPA-fallback становится требованием к раздаче статики. Неверно настроенный сервер ломает перезагрузку на вложенном маршруте, и ошибка проявляется только в проде - в разработке dev-сервер Vite делает fallback сам.
- Первая загрузка тянет весь бандл, пока не введено разбиение по маршрутам. Механизм разбиения - ленивый импорт компонента страницы в её `routes.ts`; он применяется с первого раздела, чтобы не пришлось вводить его задним числом.

## Последствия

- Новый раздел интерфейса - это папка в `src/pages/` и её `routes.ts`, подключённый в `src/router/index.ts` (раскладка и правила изоляции - ADR-0028).
- Отдельный проект-оболочка для запуска фронтенда не нужен: приложение само себе хост.
- CORS нужен в разработке, где SPA и API слушают разные порты; в проде за общим reverse proxy политика пуста (ADR-0017).
- Порт dev-сервера закреплён (`strictPort`), потому что его знают CORS-политика API и список разрешённых адресов возврата у провайдера (ADR-0023).
