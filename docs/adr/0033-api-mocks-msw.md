# ADR: Моки API через MSW (Mock Service Worker)

- Статус: Принято
- Дата: 2026-06-18
- Контекст: монорепозиторий DotnetVue3TemplateRu, фронтенд - самостоятельное SPA на Vue 3 (ADR-0027); TS-клиент генерируется Orval из OpenAPI (ADR-0026); серверное состояние - TanStack Query (ADR-0029)

## Контекст

SPA ходит в backend через сгенерированный Orval axios-клиент (`libs/frontend/api-client`). Чтобы увидеть данные в Storybook, в локальной разработке или в компонентном тесте, без моков пришлось бы поднимать весь стек через Aspire (PostgreSQL + API). Это дорого для задач, где backend не нужен: верстка экрана, демонстрация состояний (загрузка/ошибка/пусто), тест поведения поверх ответа API.

Нужен слой моков, который перехватывает HTTP-запросы клиента, не меняя сам клиент (его правило - не редактировать сгенерированный код, ADR-0026) и не завязываясь на конкретный базовый URL (его задаёт переменная сборки `import.meta.env.VITE_API_BASE_URL`, ADR-0027).

## Решение

**MSW (Mock Service Worker): моки на сетевом уровне, общие для браузера и Node, с хендлерами от Orval плюс курируемые override.**

- **Перехват на уровне сети.** MSW перехватывает запросы Service Worker-ом в браузере (Storybook, dev web) и перехватчиком в Node (Vitest). Axios-клиент не меняется; перехват идёт независимо от базового URL (паттерны хендлеров вида `*/api/...` матчат любой origin).
- **Хендлеры генерирует Orval** (`mock: { generators: [{ type: "msw" }] }` в `orval.config.ts`): рядом с каждым tag-split файлом появляется `*.msw.ts` с faker-генераторами ответов и массивами хендлеров на тег (`getNotesMock()`, `getPingMock()`). Базовый слой обновляется вместе с контрактом и покрывает все эндпоинты.
- **Курируемые override поверх faker.** Для Storybook/демо нужны осмысленные детерминированные данные, а не случайный faker. Ручные хендлеры лежат в `libs/frontend/api-client/src/mocks/overrides/<tag>/<orvalFn>.ts` (один файл - один метод, имя файла = имя сгенерированной Orval-функции) и идут в списке ПЕРВЫМИ: в MSW выигрывает первый подходящий хендлер, поэтому override перекрывают faker, а faker остаётся фолбэком для ещё не покрытых вручную эндпоинтов.
- **Расположение - в `api-client`, экспорт сабпутями.** Моки выводятся из сгенерированного клиента, поэтому живут с ним рядом, но за пределами `src/generated` (его чистит `clean: true`). Экспорт - отдельными сабпутями, чтобы рантайм-специфика не утекала в основной бандл клиента и в чужой контекст: `@dotnet-vue3-template-ru/api-client/mocks` (только данные хендлеров), `.../mocks/browser` (worker, `msw/browser`), `.../mocks/server` (server, `msw/node`).
- **Три контекста.** Storybook - через `msw-storybook-addon` (`initialize` + `mswLoader`, хендлеры по умолчанию в `parameters.msw.handlers`); dev web - опционально по флагу `VITE_API_MOCKING=enabled` (динамический импорт worker до монтирования); Vitest - глобальный `server` в `src/test/msw-setup.ts`. Браузерным контекстам нужен `mockServiceWorker.js` в их public-каталоге (генерируется `msw init`).

## Почему не альтернативы

**axios-mock-adapter (мок на уровне axios-инстанса).** Завязан на конкретный инстанс и слой axios, не работает в Storybook/тестах единообразно, и моки пришлось бы писать отдельно от контракта. MSW перехватывает на уровне сети - один набор хендлеров работает в браузере и в Node, а Orval генерирует хендлеры из того же OpenAPI.

**Отдельный mock-сервер (json-server / express).** Ещё один процесс, который надо запускать и держать в синхронизации с контрактом; не решает задачу Storybook/тестов (там нет сети наружу). MSW не требует процесса и работает во всех трёх контекстах.

**Только faker-хендлеры Orval, без override.** Минимум кода, но в Storybook данные случайные и не доменные - демонстрировать конкретные состояния нельзя. Override дают детерминизм там, где он нужен, не отменяя faker-фолбэк.

**Хендлеры в отдельном пакете `api-mocks`.** Чище граница, но +1 workspace-пакет ради файлов, которые выводятся из `api-client`. По "Simplicity First" держим рядом с клиентом и изолируем сабпутями.

## Плюсы

- Экран можно разрабатывать, демонстрировать и тестировать без backend и без Aspire.
- Один набор хендлеров на три контекста (Storybook, dev, Vitest); базовый слой генерируется из контракта и не дрейфует.
- Клиент не меняется (ADR-0026 соблюдён); перехват не зависит от базового URL.
- Рантайм-специфика (`msw/browser`, `msw/node`, faker) изолирована сабпутями и не попадает в прод-бандл клиента.

## Минусы

- Три новые зависимости (`msw`, `@faker-js/faker`, `msw-storybook-addon`).
- `mockServiceWorker.js` - сгенерированный артефакт, привязанный к версии `msw`: при апгрейде `msw` его надо перегенерировать (`msw init`) в обоих public-каталогах.
- Override - ручная поддержка: при изменении контракта осмысленные данные правятся руками (faker-слой обновляется сам).
- Сгенерированные `*.msw.ts` лежат в `src/generated` (gitignored) - перед сборкой нужна генерация клиента, как и для остального клиента.

## Последствия

- Storybook по умолчанию поднимает моки; story переопределяет ответы локально через `parameters.msw.handlers`.
- Dev без backend: `VITE_API_MOCKING=enabled yarn nx serve web`; без флага запросы идут на реальный API.
- Тесты web имеют готовый `server`; тест с особым ответом использует `server.use(http...)` и сбрасывается между тестами.
- Мок нового метода: файл по имени Orval-функции в `src/mocks/overrides/<tag>/` + строка в `index.ts` тега. Подробности - [docs/guides/api-mocks.md](../guides/api-mocks.md).
