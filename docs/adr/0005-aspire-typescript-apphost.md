# ADR: .NET Aspire с AppHost на TypeScript

- Статус: Принято
- Дата: 2026-06-09
- Контекст: монорепозиторий DotnetVue3TemplateRu, `aspire-apphost/apphost.mts`, `apps/backend/DotnetVue3TemplateRu.ServiceDefaults`

## Контекст

Локальная разработка требует поднимать одной командой целую связку: PostgreSQL,
Logto и Mailpit в Docker, backend (`DotnetVue3TemplateRu.Api`), SPA (`web`) и телеметрию,
с прозрачным service discovery (фронтенд должен узнавать адрес API без
захардкоженных портов). .NET Aspire решает ровно эту задачу - оркестрация
ресурсов, дашборд, трассировка, манифесты деплоя.

Классический способ описать оркестрацию в Aspire - это **AppHost на C#**,
отдельный .NET-проект. Но в этом монорепозитории центр тяжести инструментов
оркестрации - в Node/TypeScript: Nx, yarn workspaces, Vite, генерация
API-клиента через Orval. Заводить ради "дирижирования" ещё один C#-проект
значит держать вторую точку входа тулчейна там, где вся остальная обвязка
уже на TS.

## Решение

AppHost пишется на **TypeScript** - [aspire-apphost/apphost.mts](../../aspire-apphost/apphost.mts),
запускается через **Aspire CLI**. Используется архитектура **Guest/Host**:

- **Host** - движок Aspire остаётся на .NET: контейнеры, дашборд, трассировка,
  манифесты деплоя. Это не переписывается.
- **Guest** - `apphost.mts` выступает Node-"дирижёром": декларативно описывает
  ресурсы (PostgreSQL, Logto, Mailpit, backend, SPA) и связи между ними.

`DotnetVue3TemplateRu.ServiceDefaults` (C#) **сохраняется** - это shared-проект, который
подмешивает в .NET-сервисы Serilog, OpenTelemetry, health checks и service
discovery. Он не конфликтует с TS AppHost: AppHost оркеструет процессы,
ServiceDefaults настраивает сквозную функциональность внутри .NET-сервиса.

Service discovery работает прозрачно: фронтенд получает адрес API через
переменные окружения (`services__...` / `VITE_API_BASE_URL`), которые
прокидывает Aspire, - без захардкоженных портов.

Запуск всего стека - `yarn dev` (составной Nx-таргет `aspire-host:serve`).
Конфигурация Aspire CLI - `aspire.config.json` (SDK и пакеты
`Aspire.Hosting.JavaScript`, `Aspire.Hosting.PostgreSQL`). Logto и Mailpit
поднимаются обычными контейнерами, готовых интеграций под них не требуется.

## Почему не альтернативы

**Классический C# AppHost.**
Штатный, наиболее документированный путь Aspire. Но добавляет в монорепо
отдельный C#-проект-оркестратор там, где остальная обвязка (Nx, Vite, Orval)
живёт в Node. Это вторая модель тулинга для одной задачи. TS AppHost держит
оркестрацию в той же экосистеме, что и сборка фронтенда.

**Docker Compose / ручные скрипты запуска.**
Подняли бы контейнеры, но без дашборда Aspire, единой трассировки, service
discovery и манифестов деплоя. Пришлось бы воспроизводить это руками и
синхронизировать с конфигом backend.

**Запуск частей по отдельности (БД руками, `dotnet run`, `vite`).**
Рабочий минимум, но требует ручной координации портов и адресов между
сервисами и не масштабируется при росте числа ресурсов.

## Плюсы выбранного подхода

- Оркестрация живёт в той же TS-экосистеме, что Nx/Vite/Orval; нет отдельного
  C#-AppHost-проекта в solution.
- `yarn dev` поднимает БД, провайдер идентичности, backend и SPA с HMR
  одной командой.
- Адрес API фронтенд получает через service discovery (env), без захардкоженных
  портов - конфиг не дублируется между сервисами.
- Дашборд, трассировка и health checks - из коробки Aspire (движок остаётся
  на .NET).

## Минусы и ограничения

- Нужен установленный **Aspire CLI** - дополнительный инструмент в требованиях
  к окружению.
- В git-bash команда называется `aspire.cmd` (bare `aspire` не резолвится);
  проще запускать из PowerShell (см. README, Troubleshooting).
- TS AppHost - менее проторённый путь, чем классический C# AppHost: меньше
  примеров и материалов в сообществе.
- Для контейнеров и сборки нужны Docker и .NET SDK - окружение тяжелее, чем
  чистый Node-проект.

## Последствия

- Весь локальный стек поднимается через `yarn dev`; добавление нового
  ресурса - это правка `apphost.mts`, а не нового C#-проекта.
- `DotnetVue3TemplateRu.ServiceDefaults` остаётся обязательным для .NET-сервисов
  (телеметрия, health, discovery).
- Требования к окружению включают Aspire CLI и Docker (см. README, Требования).
