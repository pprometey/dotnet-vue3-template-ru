# ADR: Профиль durability Wolverine (Solo + message store)

- Статус: Принято
- Дата: 2026-08-11
- Контекст: backend DotnetVue3TemplateRu на Wolverine ([ADR-0012](0012-wolverine-mediator-and-messaging.md)), .NET 10, build-time экспорт OpenAPI без БД ([ADR-0026](0026-auto-generate-api.md))

## Контекст

[ADR-0012](0012-wolverine-mediator-and-messaging.md) выбрал Wolverine как медиатор/CQRS и будущую шину, но отложил вопрос: каким режимом и когда включать асинхронную и durable-обработку. Причина отсрочки - конфликт с build-time экспортом OpenAPI: полный durable требует доступной БД на старте, а экспорт (`GetDocument.Insider`) строит документ без БД.

Модель режимов Wolverine - две независимые оси:

- Глобальный `DurabilityMode`: `MediatorOnly` (только синхронный `InvokeAsync`, всё асинхронное сообщение и локальные очереди отключены) против `Solo`/`Balanced` (async-очереди включены; `Solo` - один узел без выборов лидера).
- Режим локальной очереди (доступен только вне `MediatorOnly`): `BufferedInMemory` (async, в памяти, теряется на рестарте) против `Durable` (персистентная; нужен SQL message store).

Требования: доступны и синхронный (`InvokeAsync`), и асинхронный (`PublishAsync`) вызовы; фундамент для durable/транзакционного outbox готов; build-time экспорт без БД сохранён.

## Решение

Рантайм - `DurabilityMode.Solo` + SQL message store; build-time экспорт - `Solo` без store. Переключение - профилем `Messaging:Durability` плюс guard под инструмент экспорта.

- **Два профиля, оба `Solo`** (enum `MessagingProfile`, extension `UseDotnetVue3TemplateRuDurability` в `Core.Infrastructure/Messaging`, вычисление в `Program.cs`):
  - `Persistent` (дефолт рантайма): `Solo` + `PersistMessagesWithPostgresql(connectionString, "wolverine")`. Доступны sync и async; поднят message store как фундамент durable/outbox. Служебные таблицы уходят в отдельную схему `wolverine`: так `\dt` в psql показывает предметную область, а не смесь, и очистка данных между интеграционными тестами (ADR-0031) не задевает конверты работающего durability agent.
  - `InMemory`: `Solo` без store. Async-очереди в памяти, к БД на старте не обращается.
- **Guard:** под `GetDocument.Insider` профиль форсится в `InMemory` (`Assembly.GetEntryAssembly()?.GetName().Name == "GetDocument.Insider"`). Build-time экспорт идёт без БД, а режим остаётся `Solo` - тот же, что в рантайме, отличается лишь отсутствие store. Это общий приём: стартовая зависимость, без которой сборочный сценарий обойтись может, отключается именно в нём, а не ослабляется для всех сред сразу.
- **Локальные очереди буферные (in-memory) по умолчанию.** Durable включается точечно per-queue (`UseDurableInbox` на конкретной очереди) - там, где потеря сообщения при рестарте недопустима. Первый такой кандидат - отправка уведомлений: письмо, потерянное вместе с процессом, никто не переотправит.
- **Сообщение с короткоживущим секретом durable не делается.** Команда, несущая токен доступа, в message store не кладётся: поднятая позже срока жизни токена, она упадёт на просроченном значении, а сам секрет успеет полежать в БД. Надёжность таких потоков обеспечивается доменной сверкой по статусу и идемпотентным перезапуском, а не durable-очередью.
- **Схемой message store владеет Wolverine и провизионит её сам** (`AddResourceSetupOnStartup`): создаёт и обновляет таблицы на старте. Схема не входит в EF-миграции.

## Почему не альтернативы

- **Форс `MediatorOnly` на билде.** `MediatorOnly` отключает всё асинхронное сообщение, поэтому async-конфигурация рантайма (маршруты, локальные очереди) под ним не согласуется - режим билда рассходится с рантаймом. `InMemory` сохраняет тот же `Solo`, отличаясь лишь отсутствием store, и не создаёт этого рассогласования.
- **EF-миграция таблиц Wolverine.** `MapWolverineEnvelopeStorage` помечает таблицы конвертов `ExcludeFromMigrations` и покрывает только incoming/outgoing (не dead-letters, nodes, control-queue), поэтому полную схему message store EF-миграция создать не может - Wolverine владеет своей схемой сам.
- **Глобально все очереди durable (`UseDurableLocalQueues`).** В store попали бы и сообщения с короткоживущими секретами (персист токена, отказ на просроченном). Durable вводится точечно per-queue - только там, где содержимое сообщения переживает хранение.
- **`Balanced` сейчас.** Выборы лидера и межузловая координация нужны нескольким узлам; для одного узла - `Solo` (переход на несколько узлов позже - смена одной опции).

## Плюсы

- Синхронный и асинхронный вызовы доступны одновременно; потолка `MediatorOnly` нет.
- Build-time экспорт OpenAPI без БД сохранён, а режим билда совпадает с рантаймом (`Solo`) - async-конфиг не рассогласуется.
- Durable/транзакционный outbox включается точечно per-queue поверх готового store - минимальным изменением.
- Пользовательские токены не персистятся.

## Минусы

- Профиль `Persistent` требует доступной БД на старте (dev/прод): durability agent подключается к store.
- Схема `wolverine_*` провизионится DDL-ом на старте (`AddResourceSetupOnStartup`), вне ревьюируемых EF-миграций; апгрейд Wolverine со сменой формы таблиц применяется автоматически при следующем старте. Для строгого прода, запрещающего DDL в рантайме, провизионинг переносится на deploy-команду Wolverine (storage), и тогда апгрейд требует прогнать её как шаг деплоя.
- Message store и durability agent работают, даже пока durable-потребителей нет: задел без нагрузки.

## Последствия

- Рантайм работает в `Solo`: бизнес-операции идут синхронно через `IMessageBus.InvokeAsync`; фоновые задачи - через `PublishAsync` в буферную (по умолчанию) локальную очередь. Как это применять - [guide: работа с Wolverine](../guides/wolverine.md).
- Фоновая команда, которая несёт что-то короткоживущее и непригодное для хранения (например, токен доступа), идёт на буферную очередь; при рестарте задача теряется и возобновляется идемпотентным перезапуском по статусу, а секрет в БД не попадает.
- Гарантированная доставка исходящих сообщений строится, когда понадобится, как per-queue durable + транзакционный outbox для конкретного `DbContext` того модуля, чей хендлер атомарно пишет-и-публикует tokenless-сообщение; отдельного инфраструктурного апгрейда для этого больше не требуется.
- Профиль задаётся конфигом `Messaging:Durability` (дефолт `Persistent`); значение `InMemory` - для запусков без БД.
