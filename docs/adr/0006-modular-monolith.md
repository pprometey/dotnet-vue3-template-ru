# ADR: Модульный монолит на Clean Architecture для backend

- Статус: Принято
- Дата: 2026-06-09
- Контекст: монорепозиторий DotnetVue3TemplateRu, `apps/backend/DotnetVue3TemplateRu.Api`, слои в `libs/backend/`

## Контекст

Продуктовое приложение растёт по предметным областям: у каждой свои
сущности, свои правила и свой темп изменений. Нужен
способ держать эти домены изолированными, чтобы они не превращались со
временем в переплетённый "большой ком грязи", но при этом не платить за
изоляцию операционной сложностью раздельного деплоя.

На старте проекта команда и нагрузка небольшие. Распределённая система
(микросервисы) здесь дала бы преждевременную сложность: сетевые границы между
доменами, распределённые транзакции и согласованность, отдельные пайплайны
сборки/деплоя, инфраструктуру межсервисного взаимодействия и трассировки -
всё это до того, как появятся реальные требования к независимому
масштабированию доменов.

## Решение

Backend строится как **модульный монолит на Clean Architecture**: один
исполняемый процесс (`DotnetVue3TemplateRu.Api`), внутри которого живут изолированные
**модули**. Каждый модуль - это три .NET-проекта по слоям Clean Architecture,
сгруппированных в доменную папку `libs/backend/<domain>/` (имя папки в
kebab-case: `core`, `price-list`); проекты названы по схеме
`DotnetVue3TemplateRu.<Module>.<Layer>` (PascalCase сохраняется):

- `Domain` - сущности и бизнес-правила, без внешних зависимостей;
- `Application` - use-cases, абстракции (интерфейсы), Wolverine-handlers;
- `Infrastructure` - EF Core, репозитории, внешние интеграции.

Зависимости между слоями строго направлены внутрь:

```text
Api  ->  Application  ->  Domain
Infrastructure  ->  Application / Domain
```

Связываются слои через ссылки в `.csproj`; направление зависимостей и границы
модулей охраняются архитектурными тестами на NetArchTest (ADR-0015), так же как границы
фронтенд-модулей. `apps/backend/` содержит **только точки входа**, вся
бизнес-логика - в `libs/backend/`.

На старте есть один модуль - `Core`. Новые модули (`Billing`, `PriceList`
и т.д.) добавляются **скриптом**
[scripts/add-new-module.sh](../../scripts/add-new-module.sh), а не вручную -
чтобы обвязка (три проекта, ссылки слоёв, запись в solution, `project.json`
для Nx, подключение `Application` + `Infrastructure` к Api) была одинаковой и
не разъезжалась от модуля к модулю. Подробности - в
[guide: добавить backend-модуль](../guides/add-backend-module.md).

## Почему не альтернативы

**Микросервисы.**
Дают независимый деплой и масштабирование доменов, но ценой сетевых границ,
распределённых транзакций, отдельной инфраструктуры межсервисного
взаимодействия и пайплайнов на каждый сервис. На текущем масштабе это
преждевременная сложность без окупающей пользы. Модульные границы внутри
монолита оставляют путь к выделению сервиса позже, если конкретный домен
этого реально потребует.

**Монолит без модульных границ (классические слои на всё приложение).**
Проще на старте, но домены быстро срастаются: бизнес-логика одного домена
начинает напрямую дёргать сущности другого, и изоляцию потом не восстановить.
Модульная раскладка фиксирует границы с первого дня.

**Модули без Clean Architecture (всё в одном проекте на модуль).**
Меньше проектов, но теряется направление зависимостей: инфраструктура
(EF Core, внешние API) протекает в бизнес-правила. Разделение
`Domain / Application / Infrastructure` держит домен чистым и тестируемым в
отрыве от инфраструктуры.

## Плюсы выбранного подхода

- Изоляция доменов без распределённой системы: рефакторинг и транзакции
  остаются локальными, в одном процессе и одной БД.
- Направление зависимостей (`Domain` ни от чего не зависит) делает бизнес-
  логику тестируемой и устойчивой к смене инфраструктуры.
- Единообразие модулей гарантируется скриптом, а не дисциплиной разработчика.
- Модульные границы оставляют дверь для точечной эволюции отдельного модуля
  (например, перевод отдельного модуля на event sourcing) без перекройки остального.
- Границы проверяются автоматически (архитектурные тесты, ADR-0015), а не только
  ревью.

## Минусы и ограничения

- Три проекта на модуль - оверхед даже для простого домена; на каждый модуль
  больше файлов и ссылок, чем у плоского монолита.
- Дисциплина границ требует, чтобы межмодульное взаимодействие шло через
  явные контракты, а не прямые ссылки на чужой `Domain`.
- Один процесс и одна БД: домены пока не масштабируются и не деплоятся
  независимо (осознанный компромисс, обратимый через выделение модуля в сервис).

## Последствия

- Новый домен добавляется командой `scripts/add-new-module.sh <Module>`,
  после чего остаётся ручная часть (DI в `Program.cs`, NuGet-пакеты слоёв) -
  см. [guide](../guides/add-backend-module.md).
- Имена Nx-проектов имеют префикс модуля (`core-domain`, `billing-domain`,
  ...), поэтому при нескольких модулях имена не конфликтуют.
- Бизнес-логика никогда не живёт в `apps/backend/` - только точки входа;
  вся логика - в `libs/backend/<domain>/`.
