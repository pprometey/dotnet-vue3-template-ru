# ADR: long сериализуется строкой

- Статус: Принято
- Дата: 2026-06-17
- Контекст: монорепозиторий DotnetVue3TemplateRu, проект `apps/backend/DotnetVue3TemplateRu.Api` (.NET 10), нативный OpenAPI + Orval-клиент, фронтенд на TypeScript/JS

## Контекст

C# `long` (`int64`) доходит до ~9.2 _ 10^18. В JavaScript все числа - это `Number` (IEEE-754 double), который безопасно держит целые только до 2^53-1 (~9 _ 10^15). Идентификаторы, snowflake-подобные ключи, значения из внешних систем легко выходят за этот порог.

Ключевой момент - **где** теряется точность. Потеря происходит уже на `JSON.parse`, то есть в момент, когда браузер разбирает пришедший JSON. Если в теле ответа лежит число:

```json
{ "id": 9223372036854775807 }
```

то `JSON.parse` вернёт `9223372036854776000` - значение испорчено ещё до того, как мы присвоили его какой-либо переменной. TS-типы существуют только во время компиляции, в рантайме их нет, и спасти уже округлённое число они не могут. Вывод: **одного TS-типа `string` недостаточно** - значение должно физически прийти строкой в самом JSON ("по проводу"):

```json
{ "id": "9223372036854775807" }
```

Строку `JSON.parse` не трогает, точность сохраняется. Значит, вмешаться нужно в сериализацию на бэкенде (источник контракта), а не только в типы на фронте.

Ограничения стека: проект на нативном `Microsoft.AspNetCore.OpenApi` с build-time экспортом документа для Orval (ADR-0026). Решение должно одинаково чинить и реальный JSON (рантайм), и OpenAPI-схему (контракт), иначе спека разойдётся с поведением и Orval сгенерирует неверный тип.

## Решение

`long` всегда сериализуется JSON-строкой и в TS-клиенте получает тип `string`. Механизм - две согласованные половины, обе подключены глобально в `Program.cs`.

**1. Кастомный `JsonConverter` чинит рантайм.** `System.Text.Json` даёт ровно один штатный механизм вмешаться в сериализацию типа - `JsonConverter<T>`. Конвертеров два ([`Serialization/LongAsStringJsonConverter.cs`](../../apps/backend/DotnetVue3TemplateRu.Api/Serialization/LongAsStringJsonConverter.cs)):

- `LongAsStringJsonConverter` - для `long`;
- `NullableLongAsStringJsonConverter` - для `long?` (`null` остаётся `null`).

На выходе (`Write`) оба пишут строку. На входе (`Read`) терпимо принимают и строку, и число - клиент может прислать как угодно. Регистрация через `AddControllers().AddJsonOptions(...)` встраивает их в `JsonSerializerOptions`, которым ASP.NET сериализует тело **каждого** ответа контроллеров - поэтому правило работает автоматически для любого `long`/`long?` без правок DTO.

**2. Schema-transformer чинит контракт.** Кастомный конвертер меняет рантайм, но не меняет OpenAPI-схему: .NET-генератор смотрит на C#-тип и всё равно пишет `integer / int64`. Парный [`Int64AsStringSchemaTransformer`](../../apps/backend/DotnetVue3TemplateRu.Api/Serialization/Int64AsStringSchemaTransformer.cs) (подключён через `AddOpenApi(options => options.AddSchemaTransformer<...>())`) заменяет в документе `integer/int64` на `string`, сохраняя признак `nullable`. После этого спека совпадает с рантаймом, и Orval генерирует TS-тип `string`.

Итог - две половины: конвертер чинит то, что летит по проводу; трансформер чинит то, что обещано в контракте; они не расходятся. Менять `orval.config.ts` не нужно - спека уже содержит `string`.

Смежный случай - `int32`. Веб-дефолты `System.Text.Json` (`JsonSerializerDefaults.Web` включает `JsonNumberHandling.AllowReadingFromString`) заставляют .NET описывать любое целое как union `integer | string` с числовым pattern: контракт отражает толерантный вход - сервер примет и `5`, и `"5"`. Это касается только приёма, в ответ `int32` всегда уходит числом. Для `int64` union переопределяет трансформер выше (в `string`); для `int32` его снимает парный [`Int32AsNumberSchemaTransformer`](../../apps/backend/DotnetVue3TemplateRu.Api/Serialization/Int32AsNumberSchemaTransformer.cs) - убирает `string` из union и очищает pattern, оставляя чистое `integer` (Orval -> `number`). `int32` безопасно ложится в JS `Number` (~2.1 \_ 10^9, много ниже 2^53-1). Трансформер меняет только контракт: рантайм-толерантность приёма сохраняется (сервер по-прежнему примет строку). Это тот же принцип, что у `long`: в тип идёт каноническая форма значения, а не признак толерантности приёма - `Read` у `LongAsStringJsonConverter` тоже принимает и число, и строку, но тип `string`, не `string | number`. `double`/`decimal` (тип `number`) трансформер не трогает: `decimal` теряет точность в JS так же, как `int64`, его нормализация - отдельный вопрос.

| Что                                                               | Где подключается                           | Что делает                                 |
| ----------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| `LongAsStringJsonConverter` / `NullableLongAsStringJsonConverter` | `AddControllers().AddJsonOptions(...)`     | реальный JSON по проводу: `long` -> строка |
| `Int64AsStringSchemaTransformer`                                  | `AddOpenApi(... AddSchemaTransformer ...)` | OpenAPI-документ: `int64` -> `string`      |
| `Int32AsNumberSchemaTransformer`                                  | `AddOpenApi(... AddSchemaTransformer ...)` | OpenAPI-документ: `int32` -> `integer`     |

## Почему не альтернативы

**Атрибут `[JsonConverter]` на каждом поле.** Точечно, но легко забыть на новом `long`-поле, засоряет каждый DTO и не даёт гарантии "по умолчанию для всего API". Глобально зарегистрированный конвертер покрывает любой `long` автоматически.

**Только сменить TS-тип на `string` (в Orval/руками), не трогая JSON.** Не работает: точность теряется на `JSON.parse` ещё до присваивания, тип в рантайме отсутствует. Значение обязано прийти строкой по проводу - чисто типовое решение лечит симптом, а не причину.

**Оставить `long` числом, городить на фронте `BigInt`.** `BigInt` не сериализуется штатным `JSON.parse`/`JSON.stringify`, заражает всю арифметику и сравнения, плохо дружит с UI-библиотеками и тем же TanStack Query. ID почти всегда нужен как непрозрачный идентификатор, а не как число для вычислений - строка проще и безопаснее.

**Только конвертер, без schema-transformer.** Рантайм отдавал бы строку, а OpenAPI обещал бы `integer` - Orval сгенерировал бы `number`, и контракт разошёлся бы с поведением. Нужны обе половины.

**Глобально сериализовать строкой вообще все числа.** Избыточно: `int`/`double` в безопасном диапазоне JS, гонять их строками - терять типобезопасность и читаемость спеки без причины. Проблема только у `int64`.

## Плюсы

- Точность `int64` не теряется нигде: значение идёт строкой и по сети, и в TS-типах.
- Работает автоматически для любого `long`/`long?` - DTO не правятся, новое поле покрыто по умолчанию.
- Контракт и рантайм согласованы: Orval честно генерирует `string`, `orval.config.ts` трогать не нужно.
- Десериализация терпима: на входе принимаются и строка, и число.

## Минусы

- `long`-значения на фронте - строки: для арифметики/сравнений нужен явный разбор (для ID, как правило, не требуется - используется как непрозрачный ключ).
- Два связанных механизма (конвертер + трансформер) надо держать в паре: правка одного без другого разводит рантайм и спеку.
- `Format: "int64"` в схеме оставлен как подсказка о происхождении значения, хотя тип уже `string` - может удивить при чтении спеки.

## Последствия

- Любой `long`/`long?` в DTO уходит JSON-строкой и приходит во фронт как `string`; отдельных действий при добавлении поля не нужно.
- Новый числовой тип с той же проблемой (например, если появится `Int128`) потребует такой же пары "конвертер + schema-transformer".
- Подробности для фронтенда - в [guide: API-клиент](../guides/api-client.md), раздел "Соглашение: long идёт строкой".
