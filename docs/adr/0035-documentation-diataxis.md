# ADR-0035: Документация в формате Diátaxis

## Статус

Принято

## Дата

2026-07-02

## Контекст

Документация проекта растёт: обзор архитектуры, спеки, гайды, ADR. Появляется потребность описывать реализацию конкретных модулей - их структуру, компоненты, сторы, контракты. Без единой формы такие документы смешивают назначения: в одном файле оказываются и вводный тур, и пошаговый рецепт, и справочник по API, и объяснение "почему так". Смешанный документ плохо служит любому из читателей - тот, кто пришёл за быстрым рецептом, продирается через теорию, а тот, кто хочет понять устройство, находит инструкции.

Нужна предсказуемая структура документации, которая разводит эти назначения и одинаково применяется к будущим модулям.

## Решение

Документация организуется по [Diátaxis](https://diataxis.fr): четыре квадранта по назначению, каждый - отдельный документ, квадранты не смешиваются в одном файле.

1. Учебник (tutorial, learning-oriented) - ведёт новичка за руку через первый опыт на живой системе.
2. Практические инструкции (how-to, task-oriented) - рецепты под конкретную задачу.
3. Справочник (reference, information-oriented) - сухое описание машинерии: структура, компоненты, контракты, параметры.
4. Пояснения (explanation, understanding-oriented) - почему так устроено, границы решений, компромиссы.

Раскладка в репозитории:

- Документация реализации модуля живёт в per-module папке `docs/<area>/<module>/` (`docs/backend/<module>/` для backend-модулей, `docs/frontend/<page>/` для разделов SPA) с индексом `README.md` и файлами `tutorial.md` / `how-to.md` / `reference.md` / `explanation.md`.
- Существующие `docs/guides/` - квадрант how-to кросс-проектного уровня (общие рецепты, не привязанные к одному модулю).
- Существующие `docs/adr/` - decision records: форма explanation про решения уровня проекта.

Общие принципы (кросс-проектные) остаются в ADR и гайдах; per-module документация ссылается на них и не дублирует. Как писать по Diátaxis - [Guide: документация по Diátaxis](../guides/documentation-diataxis.md).

## Почему не альтернативы

- Свободная форма на каждый документ - смешение назначений и дрейф: без рамки авторы кладут в один файл всё сразу, и документ перестаёт служить конкретной нужде.
- Один большой документ на модуль с разделами - квадранты мешаются под одной крышей; читателю с конкретной нуждой всё равно приходится вычленять свой раздел, а разделы тянут стиль друг друга.
- Только `guides/` и `adr/` без per-module reference/tutorial - негде держать справочник по конкретному модулю и учебник-тур; они не вписываются ни в кросс-проектный how-to, ни в decision record.

## Плюсы

- Читатель быстро находит нужный тип информации: за рецептом идёт в how-to, за устройством - в reference, за смыслом - в explanation.
- Форма масштабируется на будущие модули: тот же скелет из четырёх документов.
- Границы назначений явные - меньше документов-гибридов, которые устаревают целиком.

## Минусы

- Больше файлов на модуль, чем при одном общем документе.
- Автор должен осознанно выбрать квадрант для нового материала.
