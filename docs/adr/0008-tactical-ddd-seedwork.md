# ADR: Тактический DDD - SeedWork, value object на record, домен как источник инвариантов

- Статус: Принято
- Дата: 2026-07-06
- Контекст: модульный монолит на Clean Architecture (ADR-0006); доменные ошибки с кодами (ADR-0018); валидация FluentValidation (ADR-0019); локализация контента (ADR-0021); арх-тесты правил слоёв (ADR-0015)

## Контекст

Доменный слой уже инкапсулирован: приватные сеттеры, приватный EF-конструктор, статические фабрики, инварианты броском `DomainException` с кодом, методы-поведение. Не хватало единого тактического словаря для всего backend: не было общих базовых типов (равенство сущности по идентичности, токен оптимистичной блокировки), у каждого агрегата вручную повторялись `Id`/`Version`, value object писались как классы с ручным равенством, а часть правил (длина текста, границы периода) проверялась только валидатором команды или не проверялась вовсе. Нужен один набор тактических примитивов и одно правило размещения инвариантов, единые для всех модулей.

## Решение

**1. SeedWork - общие базовые типы в `Core.Domain/SeedWork/`.** `Entity` несёт `Id` (Guid) и равенство по идентичности: две сущности равны, если это один и тот же конкретный тип и один и тот же `Id`. `AggregateRoot : Entity` добавляет токен оптимистичной блокировки `Version` (rowversion, настраивается fluent-конфигом в Infrastructure). Сущности и агрегаты - классы, наследуют эти базы; `Id` присваивается при создании и не меняется. `Core.Domain` - общий нижний слой (на него уже ссылаются модули), поэтому SeedWork живёт там, рядом с `Errors/` и `Localization/`.

**2. Value object - C# `record` с валидирующим конструктором и get-only свойствами.** Структурное равенство record даёт равенство по значению даром. Get-only свойства закрывают обход инварианта через `with` (изменить поле нельзя, выражение не компилируется). Вложенная коллекция внутри VO оборачивается в `EquatableArray<T>` (readonly struct со сравнением по содержимому через `SequenceEqual`): авто-равенство record сравнивает поля, и когда поле - `EquatableArray`, сравнение идёт по элементам, а не по ссылке списка. Сущность моделируется классом, не record - равенство сущности по идентичности, а не по значению.

**3. Домен - источник инвариантов.** Каждое бизнес-правило проверяется в домене: в конструкторе, статической фабрике или методе-поведении, который бросает `DomainException` с кодом из каталога `ErrorCodes` модуля (ADR-0018). Правило FluentValidation на команде зеркалит доменный инвариант тем же кодом через `WithErrorCode(...)` и служит краевой проекцией ради пофайлового `400` и fail-fast до хендлера. Когда одно правило нужно обеим сторонам, оно описывается один раз - статическим guard-предикатом над примитивами (например `TimeRange.IsValid(start, end)`), который зовут и конструктор VO (бросает), и валидатор (как `bool`).

**4. Хранение VO с коллекциями - через ValueConverter и суррогатные DTO.** Value object с вложенной коллекцией (record'ы с `EquatableArray`) кладётся в одну JSON-колонку `ValueConverter`-ом; сериализация идёт через суррогатные DTO со списками, которые держат стабильную JSON-форму, а маппинг между формой хранения и доменным VO явный. `ValueComparer` по record-равенству отслеживает изменение колонки; такой объект неизменяем и заменяется целиком.

## Почему не альтернативы

**Базовый класс `ValueObject` с `GetEqualityComponents`.** Даёт структурное равенство, но многословен для каждого VO; C# `record` покрывает ту же потребность из коробки, а обёртка `EquatableArray<T>` закрывает единственный пробел - равенство по содержимому вложенной коллекции.

**Позиционный record для VO** (`record TimeRange(TimeOnly Start, TimeOnly End)`). Его сгенерированный конструктор не валидирует, а `init`-сеттеры пускают `with`, собирающий невалидный экземпляр. Get-only свойства плюс один валидирующий конструктор оставляют единственный путь создания и делают объект всегда валидным.

**Сущность как record.** Структурное равенство приравняло бы две разные строки с одинаковыми полями и путало трекинг EF Core, который опирается на идентичность. Сущность - класс с равенством по `Id`.

**Правило только в валидаторе команды.** Домен перестаёт быть источником истины: прямой доменный вызов или внутренний путь без валидатора пропустит невалидное состояние. Инвариант живёт в домене, а валидатор его зеркалит.

**Owned-JSON (`OwnsOne(...).ToJson()` + `OwnsMany`) для такого VO.** Owned-коллекция требует материализуемого навигационного свойства, несовместимого с неизменяемым `EquatableArray`. `ValueConverter` делает VO непрозрачным для EF значением (строка + компаратор), а форму хранения держат суррогатные DTO.

## Плюсы

- Один тактический словарь для всех модулей: сущность - класс с равенством по Id, VO - record; `Id`/`Version` не повторяются руками.
- Объект всегда валиден: единственный путь создания - валидирующий конструктор/фабрика; `with` не обходит инвариант.
- Инвариант живёт в домене и проверяется независимо от транспорта; валидатор даёт пофайловый `400`, но не является единственным местом правила.
- Равенство VO корректно, включая вложенные коллекции (`EquatableArray`), без ручного `GetEqualityComponents`.

## Минусы

- Правило, общее для домена и валидатора, выражается двумя вызовами общего предиката (домен бросает, валидатор возвращает `bool`) - но предикат один.
- VO с коллекцией, хранящийся в JSON, требует суррогатных DTO и явного маппинга в конвертере вместо прямого owned-маппинга EF.
- `EquatableArray<T>` требует, чтобы элемент сам имел значимое равенство (`IEquatable<T>`), что для доменных record выполняется автоматически.

## Последствия

- Сущности/агрегаты обоих модулей наследуют `Entity`/`AggregateRoot`; `Version` (rowversion) живёт на `AggregateRoot`, его наследуют корни с оптимистичной блокировкой. Арх-тест (ADR-0015) запрещает объявлять сущность (наследника `Entity`) record'ом.
- Новый VO - `sealed record` с валидирующим конструктором и get-only свойствами; коллекция внутри - `EquatableArray<T>`.
- Новое бизнес-правило добавляется в домен (бросок `DomainException` с кодом); если у операции есть валидатор, правило зеркалится в нём тем же кодом; общий предикат выносится статическим методом над примитивами.
- Пошаговый рецепт (сущность, VO, инвариант) - [guide: моделирование домена](../guides/domain-modeling.md).
