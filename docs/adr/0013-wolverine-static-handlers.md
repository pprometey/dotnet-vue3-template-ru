# ADR: Wolverine-хендлеры как static-классы

- Статус: Принято
- Дата: 2026-07-07
- Контекст: монорепозиторий DotnetVue3TemplateRu, backend - Wolverine как медиатор/CQRS (ADR-0012), Application-слой модулей

## Контекст

Wolverine находит хендлер по соглашению - по имени типа `*Handler` и методу `Handle`/`Handles` - и
одинаково поддерживает как instance-класс с обычным методом, так и static-класс со static-методом.
Обычная привычка из mediator-библиотек - писать хендлер instance-классом с конструктором.
Здесь она не окупается: ни один хендлер конструктор не использует, все зависимости приходят
параметрами метода `Handle` (method injection), а обнаружение и вызов идут одинаково для обоих
вариантов.

Официальная документация Wolverine (https://wolverinefx.net/guide/handlers/,
https://wolverinefx.net/introduction/best-practices) явно предпочитает static: "using a static
method as your message handler can be a small performance improvement by avoiding the need to
create and garbage collect new objects at runtime". Причина в модели выполнения - Wolverine не
резолвит хендлер через IoC-контейнер и не вызывает его через интерфейс на каждое сообщение, а
генерирует код (codegen), который напрямую вызывает метод хендлера и подставляет зависимости в его
параметры; static-метод ложится на эту модель без промежуточного создания и последующей сборки
мусора экземпляра класса. Дополнительный эффект - хендлер как чистая функция входа (команда/запрос

- зависимости на входе, результат на выходе) проще покрывать unit-тестами без моков состояния
  экземпляра.

Instance-классы Wolverine тоже поддерживает: instance хендлера создаётся на одно сообщение и
уничтожается по завершении обработки, что оправдано, когда зависимость должна резолвиться один раз
в конструкторе на весь жизненный цикл обработки этого сообщения. Ни в одном хендлере проекта такой
необходимости нет.

## Решение

**Хендлер Wolverine (Application-слой) - `public static class *Handler` со `public static`
методом `Handle(...)`; зависимости - только параметрами метода, без конструктора.**

- Команда/запрос - первый параметр метода `Handle`; дальше - сервисы из IoC-контейнера, `Envelope`,
  `IMessageContext`/`IMessageBus`, `CancellationToken`, при необходимости текущее время
  (`DateTime`/`DateTimeOffset`) - все они допустимы и для static, и для instance метода.
- Приватные вспомогательные методы внутри хендлера - тоже `static` (не используют состояние
  экземпляра, которого у static-класса и нет).
- Исключение - FluentValidation-валидаторы (`*CommandValidator : AbstractValidator<TCommand>`):
  они остаются instance-классами, так как наследуют `AbstractValidator<T>` и не подпадают под
  конвенцию хендлеров Wolverine.

## Почему не альтернативы

**Оставить instance-классы с method injection (статус-кво).** Работает так же корректно - Wolverine
не проверяет и не требует static. Но официальная рекомендация фреймворка отдаёт предпочтение static
именно по причине производительности и codegen-модели, а в проекте нет ни одного хендлера, которому
нужен был бы конструктор - цена перехода на static нулевая (нет DI-логики для миграции), а выгода
(меньше аллокаций, соответствие рекомендации фреймворка) достаётся бесплатно.

**Instance-классы с constructor injection.** Официальная документация описывает это как более
церемонный и затратный по рантайму вариант ("more code and more runtime overhead"); оправдан только
когда зависимость обязана резолвиться один раз на сообщение - такого сценария в проекте нет.

## Плюсы

- Соответствие официальной рекомендации Wolverine: меньше аллокаций и сборки мусора на хендлер за
  счёт отказа от создания instance на каждое сообщение.
- Хендлер как чистая функция входа - проще писать unit-тесты без моков состояния экземпляра.
- Правка нулевого риска: ни один хендлер не использовал конструктор, поведение и сигнатуры не
  меняются, меняется только модификатор `static` на классе и методе.

## Минусы

- Static-класс не может нести состояние экземпляра; если когда-либо потребуется зависимость,
  резолвящаяся один раз на сообщение через конструктор, такой хендлер придётся вернуть к
  instance-классу - это осознанное исключение, а не нарушение конвенции.
