# Гайд: аутентификация

Как в этом проекте устроен вход и что делать, когда операции нужен текущий пользователь. Почему так - [ADR-0023](../adr/0023-authentication-oidc.md); какой провайдер и почему - [ADR-0036](../adr/0036-identity-provider-logto.md).

## Кто что делает

Backend - resource server: он проверяет предъявленный JWT и не выпускает токены сам. Приложение настраивается двумя значениями, `Jwt:Authority` и `Jwt:Audience`, а открытые ключи забирает по JWKS из discovery-документа провайдера.

Провайдер - Logto, контейнером в Aspire. Первоначальную настройку делает скрипт `aspire-apphost/logto/bootstrap.mts`: он заводит приложение SPA, ресурс API, соединитель почты и тестовых пользователей. Скрипт идемпотентен, поэтому повторный `yarn dev` ничего не дублирует, а после удаления тома всё восстанавливается само.

| Что                            | Где                                                                          |
| ------------------------------ | ---------------------------------------------------------------------------- |
| Настройка проверки токена      | `apps/backend/DotnetVue3TemplateRu.Api/Startup/AuthenticationExtensions.cs`  |
| Заполнение контекста на запрос | `apps/backend/DotnetVue3TemplateRu.Api/Middlewares/UserContextMiddleware.cs` |
| Контракт для прикладного кода  | `Core.Application/UserContext/IUserContext.cs`                               |
| Разбор claims                  | `Core.Infrastructure/UserContext/StandardClaimsUserContextResolver.cs`       |
| Вход в SPA                     | `apps/frontend/web/src/core/auth/`                                           |
| Настройка провайдера           | `aspire-apphost/logto/bootstrap.mts`                                         |

## Адреса и тестовые пользователи

| Что                          | Адрес                        |
| ---------------------------- | ---------------------------- |
| Выдача токенов (issuer)      | `http://localhost:3481/oidc` |
| Консоль администратора Logto | `http://localhost:3482`      |
| Почта, пойманная локально    | `http://localhost:8425`      |

| Логин   | Пароль          | Почта               |
| ------- | --------------- | ------------------- |
| `alice` | `Passw0rd!2026` | `alice@example.com` |
| `bob`   | `Passw0rd!2026` | `bob@example.com`   |

Учётную запись администратора Logto заводят один раз руками при первом открытии консоли: она нужна только чтобы посмотреть настройки, приложение без неё работает.

## Как получить токен для curl

Пользовательский вход идёт только через браузер: Logto выдаёт токен по authorization code с PKCE и пароль по HTTP не принимает. Для ручной проверки защищённого эндпоинта проще всего взять токен из уже вошедшего SPA - он лежит в `sessionStorage` вкладки под ключом, начинающимся на `oidc.user:`.

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:5249/api/v1/session-context
```

Если нужен токен без браузера, заведите в консоли Logto приложение типа machine-to-machine, выдайте ему доступ к ресурсу `https://api.dotnet-vue3-template-ru.local` и запросите токен по client credentials.

## Токен доступа несёт идентичность, а не профиль

Токенов два, и задачи у них разные. ID-токен отвечает на вопрос "кто этот человек" и несёт почту и имя; он предназначен SPA. Токен доступа отвечает на вопрос "что предъявителю позволено" и уходит в API; профильных claims в нём нет.

Отсюда правило: почту и имя показывает фронтенд, беря их из ID-токена (`user.profile.email`). Бэкенд их не получает и в ответах не отдаёт.

## Что доступно прикладному коду

`IUserContext` несёт две вещи: `IsAuthenticated` и `UserId` (значение claim `sub`).

Прав в нём нет намеренно. Право обычно привязано к области - к записи, проекту, группе, - а не к человеку целиком, и плоский список в токене такую модель не выражает. Поэтому доступ проверяет обработчик предметного модуля по своим данным, а не по списку в токене.

## Как написать операцию, которой нужен текущий пользователь

Идентичность снимает край - контроллер - и кладёт явным полем в команду. Обработчик окружающий контекст не читает ([ADR-0011](../adr/0011-api-application-boundary.md)).

```csharp
[HttpPost("archive")]
public async Task<ActionResult<DocumentResult>> Archive(
    [FromBody] ArchiveDocumentRequest request,
    CancellationToken ct)
{
    var command = new ArchiveDocumentCommand(request.DocumentId, _userContext.UserId);
    return Ok(await _bus.InvokeAsync<DocumentResult>(command, ct));
}
```

Почему не прочитать `IUserContext` прямо в обработчике: ту же операцию запускает планировщик в назначенную дату, и `HttpContext` там нет вовсе. Обработчик, читающий окружающий контекст, в фоне падает или молча берёт пустое значение.

## Защита эндпоинта

Глобальной политики нет - публичные эндпоинты (health, список культур, демо) остаются доступны. Защита включается атрибутом:

```csharp
[Authorize]
public class SessionContextController : ControllerBase
```

Политики авторизации ASP.NET появятся вместе с первым правом, которое имеет смысл вне предметной области. Правило доступа внутри области - доменное, и живёт в обработчике.

## Токены в тестах

Интеграционные тесты к провайдеру не ходят: это удвоило бы длительность прогона ради проверки чужого сервиса. Фабрика подменяет параметры проверки на тестовый RSA-ключ, а `TestTokens.Issue` подписывает им токен - подпись остаётся асимметричной, симметричного секрета нет и здесь.

```csharp
var client = factory.CreateClient();
client.DefaultRequestHeaders.Authorization =
    new AuthenticationHeaderValue("Bearer", factory.IssueToken(subject: "user-1"));
```

Непроверенным остаётся ровно одно звено - получение ключей по JWKS из discovery-документа. Это осознанный размен, записанный в [ADR-0031](../adr/0031-integration-tests.md).

Разбор claims проверяется отдельно и без хоста - `tests/DotnetVue3TemplateRu.Core.Infrastructure.UnitTests/UserContext/`. Путь целиком, от заголовка до ответа, закрывает `SessionContextEndpointTests`.

## Ловушки

**SPA обязана передавать индикатор ресурса.** `VITE_OIDC_RESOURCE` уходит параметром `resource` в запросах на авторизацию и на выдачу токена. Без него Logto возвращает непрозрачную строку вместо JWT, и API отвечает 401, хотя вход прошёл успешно.

**`MapInboundClaims` обязан быть выключен.** По умолчанию ASP.NET переименовывает стандартные claims в длинные URI, и `sub` превращается в `ClaimTypes.NameIdentifier`. Резолвер, ищущий claim `sub`, тогда молча вернёт пустой `UserId`: запрос отработает с кодом 200 и пустой идентичностью, а не с ошибкой.

**Идентификатор клиента непостоянен.** Logto выдаёт его сам при создании приложения, поэтому в `.env.development` его нет. Под `yarn dev` значение подставляет AppHost. Для запуска SPA отдельно (`nx serve web`) возьмите значение из консоли Logto и положите в `.env.local`. Реестр приватных файлов - [гайд по локальной конфигурации](local-configuration.md).

**Адрес провайдера закреплён в четырёх местах** - `apphost.mts`, `Jwt:Authority` в конфигурации API, список адресов возврата в Logto и `VITE_OIDC_AUTHORITY`. Расхождение проявится не ошибкой сборки, а отказом входа или отказом CORS.

**`appsettings.Local.json` перебивает переменные Aspire.** Забытый файл с устаревшим `Jwt:Authority` уводит API мимо поднятого Logto, и все защищённые запросы начинают возвращать 401 без внятной причины.

## Что решается отдельно

Локальная запись пользователя - сущность с `sub`, почтой и именем - появится вместе с первым предметным модулем и его моделью доступа. Тогда же `/api/v1/session-context` начнёт читать профиль из базы, а не отдавать одну идентичность из токена.
