# ADR: Инфраструктура фронтенд-тестов (Vitest)

- Статус: Принято
- Дата: 2026-06-18
- Контекст: монорепозиторий DotnetVue3TemplateRu, фронтенд - самостоятельное SPA на Vue 3 (ADR-0027)

## Контекст

Бэкенд покрыт двумя видами тестов: интеграционными (ADR-0031) и архитектурными (ADR-0015). Фронтенду нужен свой инструмент: в `apps/frontend/web` есть Vue-компоненты и композаблы, и без тест-раннера проверить их нечем.

[Стратегия тестирования](../spec/test-strategy.md) сознательно ставит во главу угла интеграционные тесты API, а массовые UI-тесты откладывает - чтобы команда без опыта не выгорела, гоняясь за покрытием на геттерах и разметке. Это решение остаётся в силе. Но "отложить массовое покрытие" - не то же самое, что "не иметь возможности написать тест": когда в композабле появляется нетривиальная логика (а это первый кандидат на юнит-тест по той же стратегии), её нужно где-то проверить.

Задача этого ADR узкая: поднять рабочую инфраструктуру юнит/компонентных тестов и зафиксировать один smoke-тест, который доказывает, что она работает. Не вводить порог покрытия, не покрывать существующие компоненты ретроспективно. Ограничения - те же, что и везде в проекте: "Simplicity First" (не тащить инструменты "на будущее") и согласованность со стеком (Vite + Vue 3).

## Решение

**Vitest + happy-dom + @vue/test-utils, по образцу остального фронтенд-тулинга проекта.**

- Тест-движок - **Vitest**: нативен для Vite (тот же конфиг плагинов и резолвинг, что и у сборки), быстрый, ESM-first. Версия зафиксирована как `3.2.4` - ровно та, что и так присутствует транзитивно через Storybook, чтобы в репозитории был один Vitest.
- Среда - **happy-dom**: легче jsdom, достаточна для рендеринга компонентов.
- Монтирование компонентов - **@vue/test-utils** (`mount`); дополнительно ставится **@testing-library/vue** для тестов, ориентированных на поведение и доступность. Smoke-тест держим на `@vue/test-utils` как на более простом и наглядном входном пороге.
- Покрытие - провайдер **v8** (`@vitest/coverage-v8`), запуск через `--coverage`, отчёт (`text` + `html`) в общий `coverage/apps/frontend/web`. Порог не задаётся: измерять можно, но провал по проценту - нет.
- Конфиг - отдельный `apps/frontend/web/vitest.config.ts`, а не секция в `vite.config.ts`: сборочный конфиг отвечает за прод-бандл (разбиение по маршрутам, тема, base URL), тест-конфиг - за среду и покрытие; смешивать их - лишний риск сломать сборку правкой теста.
- `element-plus` инлайнится (`test.server.deps.inline`), а CSS отключён (`test.css: false`): пакет тянет `.scss` из исходников, и без инлайна Node-загрузчик падает на расширении `.scss`; инлайн отдаёт импорты стилей Vitest, где они заменяются пустыми модулями.
- Nx-таргет `test` задан через `nx:run-commands` (`vitest run --config ...`) - тем же исполнителем, что уже используют таргеты `lint` и `storybook` в этом проекте. Глобалы Vitest выключены (`globals: false`): `describe/it/expect` импортируются явно, поэтому `eslint.config.mjs` править не нужно.

Инфраструктура заводится только в `apps/frontend/web` - единственном проекте с Vue-компонентами. `api-client` генерируется Orval, и сгенерированный код не тестируется.

## Почему не альтернативы

**`@nx/vite:test` (штатный исполнитель Nx) вместо `nx:run-commands`.** Установленный `@nx/vite` 20.3.3 рассчитан на Vitest 1/2; с Vitest 3 исполнитель падает молча (несовпадение peer-диапазонов видно ещё на `yarn install`). Запуск `vitest run` через `nx:run-commands` обходит несовместимость, даёт читаемый вывод и совпадает с тем, как в этом же `project.json` заданы `lint` и `storybook`.

**Jest.** Зрелый и популярный, но не нативен для Vite: нужен отдельный transform (babel/ts-jest), своя трактовка ESM и `.vue`, дублирующая то, что Vite уже делает для сборки. Vitest переиспользует конфиг Vite и работает быстрее на этом стеке.

**jsdom вместо happy-dom.** jsdom полнее по реализации DOM, но тяжелее и медленнее. Для smoke-теста и юнитов композаблов хватает happy-dom; при упоре в нехватку API DOM на jsdom можно перейти точечно.

**Секция `test` прямо в `vite.config.ts`.** Меньше файлов, но сборочный конфиг externalize-ит ключевые пакеты под библиотечный бандл - в тестах это поведение не нужно и сбивает с толку. Отдельный файл разводит сборку и тесты.

## Плюсы

- На фронтенде появляется рабочий способ написать тест там, где он нужен (логика композаблов), не пересматривая стратегию "не гнаться за покрытием".
- Стек однороден с инструментами проекта: Vitest переиспользует Vite-конфиг, Nx-таргет - тем же `nx:run-commands`, что и `lint`/`storybook`; результат кэшируется Nx и виден `nx affected`.
- Один Vitest в репозитории (та же версия, что у Storybook) - меньше дрейфа версий.
- Smoke-тест документирует минимальный рабочий пример компонентного теста.

## Минусы

- Ещё пять dev-зависимостей и отдельный тест-конфиг на фронтенде.
- Инлайн `element-plus` и `css: false` - компромисс под `.scss` в этом пакете; новые внешние пакеты со стилями в исходниках могут потребовать добавления в `inline`.
- `@nx/vite:test` не используется - при будущем апгрейде `@nx/vite`/Vitest стоит пересмотреть, не вернуться ли к штатному исполнителю.

## Последствия

- Тесты лежат рядом с кодом как `*.spec.ts` (или `*.test.ts`); `nx.json` уже исключает их из `production`-инпутов, так что сборку они не затрагивают.
- Запуск: `nx test web` (или `yarn test` для всех проектов с таргетом `test`), покрытие - `nx test web --coverage`. Подробности и примеры - [docs/guides/frontend-tests.md](../guides/frontend-tests.md).
- Когда в композабле появляется нетривиальная логика - её закрывают юнит-тестом по этой инфраструктуре; массовое покрытие UI по-прежнему отложено (ADR-0031, стратегия тестирования).
- Расширение на будущие фронтенд-проекты - тем же образцом (свой `vitest.config.ts` + таргет `test` через `nx:run-commands`).
