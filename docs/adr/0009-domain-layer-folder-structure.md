# ADR: Структура Domain-слоя - Models/Repositories по сущности

- Статус: Принято
- Дата: 2026-07-06
- Контекст: модульный монолит на Clean Architecture (ADR-0006); группировка backend по фича-слайсам (сущностям); структура Application-слоя (ADR-0010); тактический DDD - SeedWork, VO, инварианты (ADR-0008)

## Контекст

Domain-слой держит агрегаты, их value object, таблицы переводов, входные data-записи и интерфейсы репозиториев. При группировке по сущности всё это лежало в одной плоской папке сущности вперемешку. Нужна самодокументируемая раскладка, где сразу видно, что модель, а что контракт хранилища, единая для всех сущностей и обоих модулей.

## Решение

**Папка-агрегат делится на `Models/` и `Repositories/`; namespace зеркалит папку.**

- **`Models/`** - агрегат, его value object, таблицы переводов (`<Entity>Localization`), входные data-записи (`DocumentHeaderData`) и дочерние сущности агрегата (`DocumentLine`).
- **`Repositories/`** - интерфейсы write-репозиториев агрегата (`IDocumentRepository`).
- **Namespace зеркалит папку** (правило репо): `...<Entity>.Models` / `...<Entity>.Repositories`. Интерфейс в `Repositories/` подключает `using ...<Entity>.Models;` для ссылки на агрегат.
- **Делятся только папки-агрегаты** (агрегат + репозиторий). Группа value object без агрегата (например, `Scheduling/` с периодичностью и сроком) и общий нижний слой (`SeedWork/`, `Errors/`, `Localization/`) остаются плоскими - разбивать их на `Models/` без `Repositories/` искусственно.
- **Только Domain.** Application остаётся по ADR-0010: read-порт (`I<Entity>QueryRepository`) в корне папки сущности, операции в `Commands/<Op>/` и `Queries/<Op>/`. Слои несут разное содержимое, поэтому и раскладка разная.

## Почему не альтернативы

**Плоская папка сущности.** При росте числа типов агрегат, VO, переводы, входные записи и контракт хранилища сваливаются в кучу, и роль файла не читается структурой. Подпапки `Models/`/`Repositories/` делают срез сущности обозримым.

**Физические подпапки без углубления namespace.** Разошлось бы с правилом репо "namespace зеркалит папку" и потребовало бы точечного исключения и подавления анализатора. Зеркалирование держит одно правило для всего репо.

**Симметрично перестроить и Application** (read-порт в `Repositories/`). Конфликтует с уже принятой в ADR-0010 раскладкой Application по операциям (`Commands/`/`Queries/`, read-порт в корне) и множит churn ради внешнего сходства слоёв, которые несут разное.

## Плюсы

- Раскладка папки-агрегата самодокументируема: модель отделена от контракта хранилища.
- Единый механический шаблон для всех сущностей обоих модулей.
- Namespace остаётся зеркалом папки - одно правило по всему репо.

## Минусы

- Потребитель, использующий и агрегат, и его репозиторий, подключает два using (`...Models` + `...Repositories`) там, где раньше был один.
- Namespace глубже на один сегмент.

## Последствия

- По шаблону разложена демо-папка `Core.Domain/Notes/`; ядро (`SeedWork/`, `Errors/`, `Localization/`) остаётся плоским. Предметные модули заводят свои папки-агрегаты по тому же правилу.
- Есть ловушка на будущее: если тип агрегата совпадёт по имени с сегментом модульного namespace (агрегат `Document` в `DotnetVue3TemplateRu.Document`), из соседнего namespace он будет затеняться и потребует алиаса при использовании. Дешевле не создавать столкновение: модуль называется во множественном числе (`DotnetVue3TemplateRu.Documents`), агрегат - в единственном.
- Гайд по моделированию домена и правила в `.claude/CLAUDE.md` описывают эту раскладку.
