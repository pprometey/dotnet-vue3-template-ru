# ADR: Rate limiting (ASP.NET Core)

- Статус: Принято
- Дата: 2026-06-18
- Контекст: монорепозиторий DotnetVue3TemplateRu, проект `apps/backend/DotnetVue3TemplateRu.Api` (.NET 10), единый формат ошибок RFC 9457 (ADR-0017)

## Контекст

Публичные эндпоинты API (`PingController`, `NotesController`) доступны без `[Authorize]` и без ограничения частоты запросов. Это оставляет API открытым для перебора и тривиального злоупотребления (флуд от одного клиента). Нужна дешёвая базовая защита, не тянущая внешних зависимостей и инфраструктуры (Redis и т.п.).

Ограничения: уважать "Simplicity First" - не вводить распределённый стор и сложные алгоритмы, пока их не требует масштаб; встроиться в существующую веб-границу (единый формат ошибок ADR-0017, CORS), а не заводить второй путь обработки ошибок; не навязывать лимит health-эндпоинтам (`/health`, `/alive`), которые опрашиваются часто.

## Решение

**Встроенный `Microsoft.AspNetCore.RateLimiting`, именованная политика opt-in, fixed window per-IP, отказ как ProblemDetails.**

- Зависимостей не добавляем: middleware и примитивы (`System.Threading.RateLimiting`) входят в shared framework `Microsoft.AspNetCore.App`.
- Политика `"public"` (константа `RateLimitPolicies.Public`) регистрируется в `Program.cs` через `AddRateLimiter` + `AddPolicy` и партиционируется по IP клиента (`RateLimitPartition.GetFixedWindowLimiter`, ключ - `Connection.RemoteIpAddress`). Алгоритм - fixed window: один клиент получает `PermitLimit` запросов на окно `WindowSeconds`, отдельное окно на каждый IP.
- Подключение **opt-in**: эндпоинты помечаются `[EnableRateLimiting(RateLimitPolicies.Public)]` (на контроллере). Health-эндпоинты атрибута не несут и остаются без лимита.
- Параметры - из секции конфигурации `RateLimiting` (`PermitLimit`, `WindowSeconds`), связанной с `RateLimitingOptions` (дефолты 100/60) через `Configure<RateLimitingOptions>`; фабрика партиции читает их per-request из `IOptions<RateLimitingOptions>` (дёшево, singleton), что заодно позволяет переопределить лимит в тестах через DI.
- Отказ - `OnRejected` ставит `429 Too Many Requests`, добавляет заголовок `Retry-After` (из `MetadataName.RetryAfter`) и пишет тело через `IProblemDetailsService` (тот же сервис, что у `GlobalExceptionHandler`), то есть в формате RFC 9457 - единообразно с прочими ошибками API и разбирается на Orval-клиенте тем же обработчиком. Текст отказа `OnRejected` резолвит сам, по коду `common.rate_limit_exceeded` на культуре запроса, и кладёт этот же код в `errorCode`, а рядом - `traceId` для связи с логом: исключения здесь нет, перехватывать `GlobalExceptionHandler` нечего.
- `app.UseRateLimiter()` стоит после `UseCors`/`UseAuthorization` (и после авто-`UseRouting`): лимитер видит выбранный эндпоинт с атрибутом, а на ответе 429 сохраняются CORS-заголовки.

## Почему не альтернативы

**Глобальный лимитер (`GlobalLimiter`) на все запросы.** Проще, но лимитирует и health-эндпоинты, и любые будущие служебные пути без разбора; именованная политика opt-in явно перечисляет защищаемые эндпоинты и оставляет health нетронутым.

**Один общий счётчик на политику (`AddFixedWindowLimiter`) вместо партиционирования по IP.** Общий счётчик складывает запросы всех клиентов в одно окно: активный клиент исчерпывает лимит для всех. Партиционирование по IP даёт честное окно на клиента.

**Голый `429` без тела.** Минимум кода, но формат ошибки расходится с остальным API (RFC 9457). ProblemDetails через `IProblemDetailsService` сохраняет единый контракт ошибок (ADR-0017) для сгенерированного клиента.

**Распределённый rate limiting (Redis и т.п.).** Нужен при нескольких инстансах за балансировщиком, но тянет инфраструктуру и стор. Для шаблона на старте достаточно in-memory; апгрейд - при появлении горизонтального масштабирования.

## Плюсы

- Без новых зависимостей: middleware и примитивы - в shared framework ASP.NET Core.
- Базовая защита публичных эндпоинтов от перебора из коробки.
- Единый формат ошибки: `429 ProblemDetails` + `Retry-After` через тот же путь, что и прочие ошибки (ADR-0017).
- Opt-in атрибутом: явный список защищаемых эндпоинтов, health не задет; лимит конфигурируется по окружениям.

## Минусы

- In-memory счётчики: при нескольких инстансах лимит считается на каждом отдельно (не глобально). Для горизонтального масштабирования нужен распределённый стор.
- Партиционирование по `RemoteIpAddress`: за обратным прокси нужно корректно проставлять реальный IP клиента (`ForwardedHeaders`), иначе все клиенты схлопнутся в один IP прокси.
- Новый защищаемый эндпоинт нужно не забыть пометить `[EnableRateLimiting]` (плата за opt-in).

## Последствия

- Публичный эндпоинт, нуждающийся в защите, помечается `[EnableRateLimiting(RateLimitPolicies.Public)]`; параметры лимита задаются секцией `RateLimiting` в конфигурации.
- Превышение лимита отдаётся как `429 ProblemDetails` + `Retry-After`, с локализованным `detail` и кодом `errorCode`; интеграционный тест (`RateLimitingEndpointTests`) проверяет форму и локализацию, переопределяя лимит на маленький через изолированную фабрику.
- При выводе за обратный прокси в проде нужно настроить `ForwardedHeaders`, чтобы партиционирование по IP работало по реальному клиенту.
- При переходе к нескольким инстансам решение пересматривается в сторону распределённого rate limiting (новый ADR).
