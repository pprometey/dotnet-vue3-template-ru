# ADR: Структура Application-слоя - операции в Commands/Queries по подпапкам, класс на файл

- Статус: Принято
- Дата: 2026-07-06
- Контекст: модульный монолит на Clean Architecture (ADR-0006); CQRS через Wolverine (ADR-0012); валидация ввода FluentValidation (ADR-0019); группировка backend по фича-слайсам (сущностям)

## Контекст

Application-слой держит команды, запросы, их хендлеры, валидаторы, read-порты и read-модели. При группировке по сущности эти артефакты нужно разложить так, чтобы у каждой операции было одно предсказуемое место, а роль каждого типа (команда, валидатор, хендлер, результат) читалась сразу по имени файла. Нужен один шаблон, единый для всех сущностей и обоих направлений (команды и запросы), чтобы структура не разъезжалась от сущности к сущности.

## Решение

**Сущность - верхняя группировка; внутри неё операции лежат в `Commands/<Op>/` и `Queries/<Op>/`, один тип на файл.**

- **Папки по операциям.** Внутри папки сущности - `Commands/` и `Queries/`; в каждой - подпапка на операцию (`CreateNote/`, `GetNote/`). Вся операция (команда/запрос, её хендлер, валидатор, уникальный результат) лежит в своей подпапке.
- **Один тип на файл.** Команда, её хендлер и её валидатор - всегда отдельные файлы. Роль видна по имени файла: `<Op>Command.cs`, `<Op>CommandHandler.cs`, `<Op>CommandValidator.cs`, `<Op>Result.cs` (для команд); `<Op>Query.cs`, `<Op>QueryHandler.cs`, `<Op>Result.cs` (для запросов).
- **Имя типа = имя операции + суффикс роли**, без повторного префикса сущности - сущность уже задана родительской папкой и namespace (`Notes/Commands/CreateNote/CreateNoteCommand.cs`, `Documents/Queries/GetDocumentLines/GetDocumentLinesQueryHandler.cs`). Хендлеры несут суффикс `CommandHandler`/`QueryHandler`, чтобы направление читалось по имени класса.
- **Read-порт - в корне папки сущности.** `I<Entity>QueryRepository` общий для запросов сущности, поэтому лежит в корне (`Notes/INoteQueryRepository.cs`), объявлен в Application, реализуется в Infrastructure.
- **Разделяемые результаты/read-модели - в `<Entity>/Models/`.** Результат, уникальный для операции, лежит в её подпапке как `<Op>Result.cs`. Результат или проекция, которые делят несколько операций (`NoteResult` для create+get), лежат в `<Entity>/Models/`.
- **Namespace зеркалит папку** (`DotnetVue3TemplateRu.<Module>.Application.<Entity>.Commands.<Op>`). Тип из предкового namespace виден без `using`, поэтому read-порт в корне сущности доступен хендлерам операций без лишних импортов.
- **Кросс-срезовые швы-папки** (`UserContext/`, `Configuration/`) остаются как есть - это не CQRS-операции, а порты и модель, общие для сущностей.

## Почему не альтернативы

**Плоская раскладка по роли в папке сущности** (команда, хендлер, валидатор россыпью в `Notes/`). При росте числа операций папка сущности превращается в свалку разнородных файлов, а связь "команда - её валидатор - её хендлер" не выражена структурой. Подпапка на операцию делает срез самодостаточным и обозримым.

**Строгий префикс сущности в имени типа** (`NoteCreateCommand`, `DocumentGetLinesQuery`). Даёт заикание с родительской папкой (`Notes/.../NoteCreate...`) и требует переименования DTO, видимых в контракте. Имя по операции + суффикс роли самодостаточно: сущность несёт папка и namespace.

## Плюсы

- Каждая операция самодостаточна: команда, валидатор, хендлер, уникальный результат - в одной подпапке.
- Роль типа видна по имени файла - "это команда, это валидатор, это хендлер" читается без открытия файла.
- Один механический шаблон для всех сущностей и обоих модулей; новая операция кладётся однозначно.
- Имена результатов-DTO, видимые в OpenAPI/TS-клиенте, стабильны (по операции, без принудительного префикса сущности).

## Минусы

- Больше папок и файлов, чем при плоской раскладке; у операции из одного типа получается подпапка с одним файлом.
- Глубже вложенность namespace - у типов из соседних под-деревьев (напр. `Models/`) появляется лишний `using`.

## Последствия

- Демо-модуль Core разложен по этому шаблону; арх-тесты правил слоёв (ADR-0015) зелёные.
- Гайд по добавлению backend-модуля и гайд по Wolverine описывают эту раскладку; валидатор кладётся в подпапку своей команды.
- Шаблон применяется ко всем CQRS-срезам, включая `Configuration`, `SessionContext`, `Ping`.
