# ADR: Версионирование API

- Статус: Принято
- Дата: 2026-06-17
- Контекст: монорепозиторий DotnetVue3TemplateRu, проект `apps/backend/DotnetVue3TemplateRu.Api` (.NET 10), нативный OpenAPI + Orval-клиент

## Контекст

Сервис - развивающийся продукт: контракты эндпоинтов будут меняться, а у API появятся внешние потребители (собственное SPA, интеграции). Менять контракт "на месте" ломает уже работающих клиентов. Нужен явный, предсказуемый механизм версий, заложенный до появления реальных модулей, чтобы не переписывать маршруты и клиента задним числом.

Ограничения стека: проект уже на нативном `Microsoft.AspNetCore.OpenApi` (.NET 9+ заменил Swashbuckle), с build-time экспортом OpenAPI (`OpenApiGenerateDocumentsOnBuild`) как источником для Orval, и Scalar в роли dev UI. Решение по версионированию должно встроиться в этот пайплайн, а не ломать его, и не тащить лишней сложности.

## Решение

**Версия в URL-сегменте** (`/api/v1/notes`, `/api/v2/notes`) через `Asp.Versioning` 10.0 (пакеты `Asp.Versioning.Mvc` + `Asp.Versioning.Mvc.ApiExplorer`).

Конфигурация (`Program.cs`): `AddApiVersioning(UrlSegmentApiVersionReader, DefaultApiVersion=1.0, AssumeDefaultVersionWhenUnspecified, ReportApiVersions).AddApiExplorer(GroupNameFormat="'v'VVV", SubstituteApiVersionInUrl).AddMvc()`.

Два сознательных упрощения:

**1. Один контроллер на ресурс, методы помечаются версиями.** Контроллер объявляет несколько `[ApiVersion]`; метод без `[MapToApiVersion]` обслуживает все версии (неизменившийся эндпоинт не дублируется), а изменившийся эндпоинт разносится по версиям с одним маршрутом и разными C#-именами (`GetByIdV1` / `GetByIdV2` + `[MapToApiVersion("1.0")]` / `[MapToApiVersion("2.0")]`). Маршрут: `[Route("api/v{version:apiVersion}/[controller]")]`.

**2. Один общий OpenAPI-документ на все версии.** Нативный `AddOpenApi` с `ShouldInclude = _ => true` включает эндпоинты всех версий в единый документ; пути с версией подставляет `SubstituteApiVersionInUrl` на уровне API Explorer. Отдельный мост `Asp.Versioning.OpenApi` (на момент решения только pre-release `10.0.0-rc.1`) **не нужен**.

Потребление клиентом: build-time экспорт пишет один документ `DotnetVue3TemplateRu.Api.json`; Orval имеет один вход и генерирует единый плоский клиент, где версии различимы по имени функции (`getApiV1NotesId` / `getApiV2NotesId`). Соглашение: DTO разных версий имеют разные имена (`NoteResult` vs `NoteResultV2`), чтобы в общем документе не было коллизии схем.

## Почему не альтернативы

**Контроллер на версию (`NotesV2Controller`).** Каждая версия самодостаточна, но неизменившиеся эндпоинты приходится копировать в новый контроллер; при переходе v1->v2 обычно меняется 1-2 эндпоинта из многих, и все остальные пришлось бы дублировать. Один контроллер + `[MapToApiVersion]` дублирует только изменившееся.

**Документ OpenAPI на версию (`WithDocumentPerVersion`).** Рекомендованный путь `Asp.Versioning.OpenApi`, но он усложняет фронтенд-пайплайн (вход Orval на версию, `workspace`, реэкспорт версий неймспейсами) и тащит pre-release-зависимость. Один общий документ оставляет генерацию клиента простой (один вход, плоская структура), а версии всё равно различимы по URL и имени функции. Цена - документ толстеет по мере накопления версий; для сервиса, где старые версии со временем выпиливают, приемлемо.

**Версия в заголовке/query/media type.** Чистые URL, но версия невидима в адресе (труднее логировать/кэшировать/отлаживать) и хуже ложится на генерацию типизированного клиента: одинаковые пути для разных версий -> конфликт операций и схем. URL-сегмент даёт разные пути -> разные операции.

**Swashbuckle ради зрелой интеграции версий.** Откат с уже принятого нативного OpenAPI (ADR-0026). Нативный `AddOpenApi` + `ShouldInclude` закрывает задачу без смены инфраструктуры.

**Не версионировать вовсе.** Любое несовместимое изменение ломает потребителей; для развивающегося продукта неприемлемо.

## Плюсы

- Версия явная и видимая в URL: просто логировать, кэшировать, тестировать, объяснять потребителю.
- Минимум зависимостей: только стабильные `Asp.Versioning.Mvc`/`Mvc.ApiExplorer`; OpenAPI - штатный нативный, без мостов и pre-release.
- Простой клиент: один документ -> один вход Orval -> единый плоский клиент; версии различимы по имени функции (`getApiV1NotesId` / `getApiV2NotesId`).
- Неизменившиеся эндпоинты не дублируются между версиями (`[MapToApiVersion]` только на изменившихся).

## Минусы

- Общий документ растёт и смешивает версии по мере их накопления (для UI Scalar - один список со всеми эндпоинтами).
- Требуется соглашение об уникальных именах DTO между версиями (`NoteResult` / `NoteResultV2`), иначе коллизия схем в общем документе.
- Два метода одного маршрута обязаны иметь разные C#-имена (перегрузка по пути невозможна); версию различает Asp.Versioning.

## Последствия

- Все маршруты под `api/v{version}/...`; новые контроллеры объявляют `[ApiVersion]` и версионированный `[Route]`; новая версия эндпоинта - новый метод с `[MapToApiVersion]` (см. [guide: добавить backend-модуль](../guides/add-backend-module.md)).
- Dev UI Scalar (`/scalar/v1`) и сырой документ (`/openapi/v1.json`) содержат все версии.
- На старте: v1 (Ping, Notes) + демонстрационный v2 (`GET /api/v2/notes/{id}` с расширенным `NoteResultV2`; `POST` общий для v1 и v2), доказывающий мультиверсионность end-to-end.
