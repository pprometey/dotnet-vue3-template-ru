# ADR: Обработка ошибок (RFC 9457) и CORS

- Статус: Принято
- Дата: 2026-06-18
- Контекст: монорепозиторий DotnetVue3TemplateRu, проект `apps/backend/DotnetVue3TemplateRu.Api` (.NET 10), нативный OpenAPI + Orval-клиент, фронтенд - самостоятельное SPA (ADR-0027)

## Контекст

Веб-граница API требует двух базовых вещей:

1. **Единого формата ошибок.** Без единого обработчика необработанное исключение уходит клиенту как нетипизированный 500, а валидация делается вручную в контроллере (`ValidationProblem(...)`). Фронтенд-клиент генерируется Orval из OpenAPI, и предсказуемая структура ошибки нужна, чтобы разбирать её на фронте единообразно (один обработчик вместо разбора разнородных тел).
2. **CORS-политики.** В разработке SPA и API слушают разные порты (Vite на 5173, API на 5249), а разные порты одного хоста - это разные origin для браузера. Без явной политики он блокирует каждый запрос из приложения. В проде обе части обычно стоят за общим reverse proxy на одном origin, и политика оказывается пустой - но полагаться на это в конфигурации разработки нельзя.

Ограничения: не тащить лишних зависимостей и абстракций (принцип "Simplicity First"); встроиться в существующий стек (.NET 10, нативный OpenAPI), не ломая build-time экспорт документа. Структурная валидация полей (FluentValidation) - отдельное решение ([ADR-0019](0019-input-validation.md)) и в это решение не входит.

## Решение

**Ошибки - формат RFC 9457 (ProblemDetails) через нативные средства .NET.** Регистрируем `AddProblemDetails()` и единый `IExceptionHandler` (`GlobalExceptionHandler` в `apps/backend/DotnetVue3TemplateRu.Api/ExceptionHandlers/`), подключённый `app.UseExceptionHandler()` первым в конвейере. Обработчик мапит известные типы исключений в статус-коды:

| Исключение                                               | Статус |
| -------------------------------------------------------- | ------ |
| `ValidationException` (FluentValidation, поле-уровневая) | 400    |
| `DomainException` (доменный инвариант)                   | 400    |
| `ArgumentException`                                      | 400    |
| `NotFoundException` (Application-слой)                   | 404    |
| `DbUpdateConcurrencyException` (устаревший rowversion)   | 409    |
| `UpstreamUnavailableException` (смежный сервис не дал)   | 502    |
| всё остальное                                            | 500    |

Текст ошибки (Detail) клиенту по-английски не отдаётся: он локализуется по коду ошибки на культуре запроса (в ProblemDetails кладётся `errorCode`, см. [ADR-0018](0018-domain-errors-codes-and-localization.md)) - для доменных ошибок (400), `NotFoundException` (404), конфликта оптимистичной блокировки (409) и непредвиденной/прочей ошибки (500/400-fallback по сквозным кодам `common.*`). В dev fallback 5xx/прочего показывает исходный текст исключения для диагностики, в проде - обобщённое локализованное сообщение. В ответ добавляется `traceId` для корреляции; 5xx логируются как Error. Title - технический ярлык типа (RFC 9457), локализуется только Detail. Контроллеры бросают исключения вместо ручного формирования ответов. Типы исключений уровня Application - `NotFoundException` и `UpstreamUnavailableException`; оба несут `ErrorCode` + `Args`, как доменный `DomainException`. Валидационный отказ отдаётся как `ValidationProblemDetails` со словарём `errors` и кодами по полям.

**CORS - именованная политика со списком origin из конфигурации.** Политика `SpaCors` читает `Cors:AllowedOrigins` (массив) из конфигурации: пусто в `appsettings.json` (прод-доступ закрыт по умолчанию, origin задаются окружением), `http://localhost:5173` в `appsettings.Development.json` (dev-адрес SPA). Политика: `WithOrigins(...).AllowAnyHeader().AllowAnyMethod()` без `AllowCredentials` - токен передаётся заголовком `Authorization` (Bearer), не cookie. `app.UseCors("SpaCors")` стоит до `UseAuthentication`.

## Почему не альтернативы

**Своё middleware вместо `IExceptionHandler`.** `IExceptionHandler` (.NET 8+) - штатный механизм, интегрирован с `AddProblemDetails`/`IProblemDetailsService`, поддерживает цепочку обработчиков. Самописное middleware дублировало бы инфраструктуру без выгоды.

**Контроллеры формируют ошибки сами (`NotFound()`, `ValidationProblem()`).** Размазывает формат по эндпоинтам и легко рассинхронизируется; необработанные исключения всё равно остаются нетипизированными 500. Централизация в обработчике даёт один формат на все пути.

**`AllowAnyOrigin()` вместо списка.** Проще, но открывает API любому источнику - неприемлемо для сервиса, который хранит персональные данные. Список из конфигурации явный, аудируемый и разный по окружениям.

**`AllowCredentials` + cookie.** Не нужно: аутентификация идёт Bearer-токеном в заголовке (ADR-0023). `AllowCredentials` к тому же несовместим с `AllowAnyOrigin`, требует защиты от CSRF и расширяет поверхность атаки без необходимости.

## Плюсы

- Единый предсказуемый формат ошибок (RFC 9457) -> единообразный разбор на сгенерированном фронтенд-клиенте.
- Без новых зависимостей: `AddProblemDetails`, `IExceptionHandler`, `AddCors` - штатные в `Microsoft.AspNetCore`.
- Контроллеры чище: бросают исключения, не формируют ответы об ошибках вручную.
- CORS явный и конфигурируемый по окружениям; прод-доступ закрыт по умолчанию.

## Минусы

- Маппинг исключение -> статус ведётся в одном месте (`GlobalExceptionHandler`); новые типы ошибок нужно туда добавлять.
- Список origin нужно поддерживать в конфигурации прод-окружения.

## Последствия

- Новый код бросает доменные/прикладные исключения; для "не найдено" - `NotFoundException` из `DotnetVue3TemplateRu.Core.Application.Exceptions` с кодом ошибки из каталога `ErrorCodes` (текст локализуется на границе, ADR-0018). Маппинг новых типов - в `GlobalExceptionHandler`.
- Все ошибки API отдаются как ProblemDetails; интеграционные тесты проверяют форму (`ErrorHandlingEndpointTests`).
- Разрешённые origin задаются в `Cors:AllowedOrigins`. В разработке это адрес Vite; порт там жёстко закреплён (`strictPort`) именно потому, что случайный порт молча ломал бы каждый запрос из браузера. В прод-конфигурации список пуст, когда SPA и API стоят за общим reverse proxy, и заполняется, когда они разъезжаются по разным хостам.
- Структурная валидация ввода (FluentValidation) вынесена в отдельное решение [ADR-0019](0019-input-validation.md): провал валидации даёт `400` с `ValidationProblemDetails` (словарь `errors`) через тот же `GlobalExceptionHandler`.
