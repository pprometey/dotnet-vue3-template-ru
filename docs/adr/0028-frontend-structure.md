# ADR 0028: Структура фронтенда - страницы, фичи и изоляция

## Статус

Принято

## Дата

2026-08-11

## Контекст

Интерфейс растёт разделами, и каждый раздел - это ветка маршрутов с несколькими экранами: список сущностей и карточка одной из них, настройки и редактор справочника, сводный экран, история изменений.

Разделы почти не пересекаются по данным, но каждый внутри себя распадается на несколько самостоятельных кусков. На сводном экране это видно лучше всего: таблица со сводными числами; блок истории изменений; поле заметки. Это три разные вещи с разными данными, разными состояниями загрузки и разной судьбой - заметка редактируется, таблица только читается, история подгружается отдельным запросом.

Группировка по типу файла (общие `components/`, `composables/`, `stores/`) на таком объёме перестаёт помогать по двум причинам. По имени папки не видно, к какому разделу относится файл, поэтому поиск идёт перебором. И любые два куска интерфейса могут сослаться друг на друга просто потому, что лежат рядом, - через полгода блок заметки импортирует внутренний компонент сводной таблицы, и разделить их уже нельзя.

## Решение

Четыре уровня со строгим направлением импорта "вниз" плюс один кросс-раздельный слой.

1. **app** - composition root и маршрутизация: `src/main.ts`, `src/App.vue`, `src/router/`. Собирает приложение (Pinia, TanStack Query, Element Plus, i18n, OIDC) и склеивает ветки маршрутов страниц. Единственный уровень, которому можно импортировать любую страницу.
2. **core** (`src/core/`) - кросс-раздельная инфраструктура: общий каркас страницы (`layout/`), сборка i18n, OIDC-клиент и провайдер токена, bootstrap-сервисы конфигурации и сессии, тема. Прикладной логики разделов здесь нет.
3. **page** (`src/pages/<page>/`) - раздел приложения, то есть ветка маршрутов, а не один экран. Держит свой `routes.ts`, корневые компоненты экранов, стор раздела и оркестрирует свои фичи.
4. **feature** (`src/pages/<page>/features/<feature>/`) - вертикальный срез внутри раздела, главная единица роста; наружу отдаёт свои компоненты через `index.ts`.
5. **page-shared** (`src/pages/<page>/shared/`) - листья, общие для фич одного раздела. Заводится при появлении второго потребителя, не заранее.

Изоляция: страница не импортирует страницу-сестру, фича не импортирует фичу-сестру. Интеграция двух фич идёт на уровне страницы - она владеет состоянием, которое их связывает, - или через `page-shared`. Интеграция двух разделов идёт через `core` или через маршрут.

Внутри фичи - colocation: единственный публичный вход плюс `index.ts`, приватные подкомпоненты рядом с родителем, плоско по умолчанию, поднятие уровнем выше - по факту второго потребителя, а не по предчувствию.

Импорты между уровнями идут по псевдонимам путей (`@core/*`, `@pages/*`), объявленным в `apps/frontend/web/tsconfig.json`; внутри своей папки - относительные. Псевдоним - только путь: граф зависимостей `eslint-plugin-boundaries` строит по фактическому расположению файла на диске.

### Контроль границ

Набор элементов и правил в `eslint.config.mjs`. Порядок важен: выигрывает первый совпавший паттерн, поэтому специфичные (`features/*`, `shared/*`) идут перед общим `pages/*`.

```js
files: ["apps/frontend/web/src/**/*.{ts,vue}"],
settings: {
  "import/resolver": {
    typescript: { project: "apps/frontend/web/tsconfig.json" },
    node: { extensions: [".ts", ".js", ".vue", ".mjs", ".cjs"] },
  },
  "boundaries/include": ["apps/frontend/web/src/**/*"],
  "boundaries/elements": [
    { type: "app", pattern: ["apps/frontend/web/src/main.ts",
                             "apps/frontend/web/src/App.vue"], mode: "file" },
    { type: "app", pattern: "apps/frontend/web/src/router" },
    { type: "core", pattern: "apps/frontend/web/src/core/*" },
    { type: "feature", pattern: "apps/frontend/web/src/pages/*/features/*",
      capture: ["page", "feature"] },
    { type: "page-shared", pattern: "apps/frontend/web/src/pages/*/shared/*",
      capture: ["page", "segment"] },
    { type: "page", pattern: "apps/frontend/web/src/pages/*", capture: ["page"] },
  ],
},
rules: {
  "boundaries/element-types": ["error", {
    default: "disallow",
    rules: [
      { from: "app",  allow: ["core", "page"] },
      { from: "core", allow: ["core"] },
      { from: "page", allow: ["core",
          ["feature",     { page: "${from.page}" }],
          ["page-shared", { page: "${from.page}" }]] },
      { from: "feature", allow: ["core",
          ["page-shared", { page: "${from.page}" }]] },
      { from: "page-shared", allow: ["core"] },
    ],
  }],
}
```

Захват имени (`capture: ["page", ...]`) и подстановка `${from.page}` - это то, что превращает правило "фича видит только свою страницу" из пожелания в проверку: без захвата линт разрешил бы фиче импортировать `page-shared` любого чужого раздела.

Резолв импортов настроен явно двумя резолверами. `typescript` читает псевдонимы из `tsconfig paths`, `node` добирает `.vue` и импорты директорий через `index.ts`. Без alias-aware резолва цель импорта осталась бы нераспознанной, и правило молча пропустилось бы - именно поэтому настройку проверяют намеренным нарушением границы, а не чтением конфига.

## Почему не альтернативы

**Плоские `views/` + `components/` + `stores/` на весь проект.** Работает до первых двух-трёх десятков файлов. Дальше по расположению файла перестаёт быть видно, кто его владелец, и любой компонент может утащить чужой стор. В выбранной раскладке место файла определяется охватом: приватное фичи -> общее раздела -> `core`.

**Полный Feature-Sliced Design с уровнями `entities` и `widgets`.** Даёт больше слоёв, чем нужно домену с шестью разделами. Уровень `entities` окупается, когда одна и та же сущность рисуется в трёх разных разделах со своей логикой отображения; сейчас такого нет. Выбранный набор - подмножество FSD, и достроить недостающий уровень позже дешевле, чем сейчас поддерживать пустой.

**Свободные импорты между разделами "по необходимости".** Границы, которые проверяет только ревью, размываются за несколько недель: каждое отдельное нарушение выглядит безобидно, а накапливаются они в связность, которую уже не распутать. Здесь нарушение валит линт.

**Отдельный уровень `shared/` рядом с `core/`.** Разделение "инфраструктура" и "общие примитивы" на два верхних уровня оправдано при десятках общих компонентов. Сейчас потребитель один, поэтому общий уровень один - `core` со своими подпапками.

## Плюсы

- Рост идёт фичами; каждая фича самодостаточна и заменяема за своим `index.ts`.
- Границы не на словах: нарушение изоляции валит линт, а не доходит до ревью.
- Добавление раздела не требует настройки - паттерны boundaries обобщённые, новый раздел подпадает под них автоматически.
- Навигация предсказуема: место файла определяется его охватом.

## Минусы

- Больше барель-файлов, чем при плоской раскладке; для совсем мелкого раздела это избыточно.
- Интеграция двух фич требует явного механизма на уровне страницы вместо прямого импорта - чуть больше церемоний ради слабой связанности.
- Контроль границ зависит от корректной настройки резолва импортов: ошибка в ней не ломает линт, а выключает правило.

## Последствия

- Демо-раздел `pages/notes` состоит из двух фич (`create-note`, `note-view`) именно затем, чтобы правило изоляции сестёр было не декларацией: фичи не знают друг о друге, а идентификатор созданной заметки передаёт между ними страница.
- Проверка правила входит в приёмку: намеренный импорт сестры обязан валить `nx run web:lint` с `boundaries/element-types`.
- Новый раздел интерфейса - это папка в `src/pages/`, её `routes.ts` и строка в `src/router/index.ts`.
