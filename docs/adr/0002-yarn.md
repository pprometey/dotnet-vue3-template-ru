# ADR: Использование Yarn в качестве пакетного менеджера

- Статус: Принято
- Дата: 2026-06-09
- Контекст: монорепозиторий DotnetVue3TemplateRu (Nx + workspaces)

## Контекст

Проект представляет собой монорепозиторий на базе Nx с несколькими
приложениями и библиотеками, объявленными через `workspaces`
(см. `package.json`: `apps/frontend/*`, `libs/frontend/*`).

Нужен пакетный менеджер, который:

- надёжно работает с workspaces (внутренние пакеты ссылаются друг на друга);
- даёт детерминированные и быстрые установки в CI;
- фиксирует точную версию инструмента для всей команды.

Текущая конфигурация:

- `packageManager: "yarn@4.5.0"` (Yarn Berry, не классический Yarn 1.x);
- `nodeLinker: node-modules` (`.yarnrc.yml`) - привычная раскладка
  `node_modules`, совместимая с Nx, Vite и остальной экосистемой;
- `enableGlobalCache: true` - общий кэш пакетов между проектами;
- протокол `workspace:` для зависимостей внутри репозитория
  (`@dotnet-vue3-template-ru/api-client`).

## Решение

Используем Yarn 4 (Berry) как единственный пакетный менеджер проекта.
Версия зафиксирована полем `packageManager`, что через Corepack
гарантирует всем разработчикам и CI одинаковую версию Yarn без ручной
установки.

## Почему Yarn, а не NPM

1. Фиксация версии менеджера. Поле `packageManager` + Corepack дают
   единую версию Yarn у всех. У NPM версия привязана к версии Node,
   и явно её зафиксировать сложнее.
2. Workspaces. Yarn исторически имеет более зрелую и предсказуемую
   поддержку монорепозиториев, что важно для связки с Nx.
3. Детерминизм и скорость. Глобальный кэш и строгий резолвинг дают
   стабильные и быстрые установки в CI.
4. Протоколы зависимостей. `workspace:`, `portal:`, `patch:` упрощают
   работу с локальными пакетами: `workspace:*` связывает SPA с
   `api-client` внутри репозитория, `portal:` подключит соседний
   чекаут, если он понадобится, `patch:` правит чужой пакет без форка.
5. Гибкость линкера. `nodeLinker` позволяет выбрать раскладку:
   мы выбрали `node-modules` ради максимальной совместимости, сохранив
   при этом остальные преимущества Yarn 4.

## Плюсы и минусы

### Yarn 4 (Berry)

Плюсы:

- встроенная и зрелая поддержка workspaces для монорепозитория;
- версия менеджера фиксируется через `packageManager` + Corepack;
- быстрый и эффективный глобальный кэш, хорошие офлайн-установки;
- дополнительные протоколы зависимостей (`portal:`, `workspace:`, `patch:`);
- настраиваемый `nodeLinker` (node-modules или PnP);
- строгий и предсказуемый резолвинг зависимостей.

Минусы:

- отдельный инструмент - порог входа выше, чем у NPM из коробки;
- конфигурация через `.yarnrc.yml` отличается от привычного NPM;
- режим PnP несовместим с частью инструментов (поэтому выбран
  `node-modules`);
- требует Corepack или ручной установки нужной версии.

### NPM

Плюсы:

- поставляется вместе с Node.js, ничего ставить не нужно;
- максимальная совместимость и самая большая база примеров;
- `package-lock.json` обеспечивает детерминированные установки;
- поддержка workspaces присутствует в современных версиях.

Минусы:

- версия NPM привязана к версии Node, её сложнее жёстко зафиксировать;
- поддержка workspaces менее зрелая для сложных монорепозиториев;
- нет аналогов протоколов `portal:` / `patch:` из коробки;
- меньше возможностей тонкой настройки кэша и линковки.

## Последствия

- Все команды и CI работают через Yarn 4; команды NPM в проекте
  не используются.
- Для запуска достаточно включённого Corepack - нужная версия Yarn
  подтянется автоматически из поля `packageManager`.
- Раскладка `node-modules` сохраняет совместимость с Nx, Vite и
  прочими инструментами, поэтому переход на PnP пока не требуется.
