# Как работать с репозиторием

Запуск и требования к окружению - [README.md](README.md). Устройство системы - [docs/architecture.md](docs/architecture.md).

## Перед тем как писать код

Прочитайте ADR того слоя, который собираетесь трогать. Конвенции проекта живут там, и код, написанный мимо них, переписывается на ревью. Полный список - [docs/adr/README.md](docs/adr/README.md), ориентир по подсистемам - [.claude/project-map.md](.claude/project-map.md).

Читайте выборочно: для фронтенда - 0026-0033, для backend - 0006-0025. Читать все 36 ради правки в одну строку не нужно.

## Ветки и коммиты

Работа идёт в ветке от `main`. Имя ветки - по задаче: `feature/cycle-scheduling`, `fix/token-refresh`.

Сообщение коммита описывает изменение по существу, а не пересказывает диф. Русский язык, повелительное или прошедшее время - как удобнее, лишь бы единообразно внутри ветки.

## Проверки перед коммитом и пушем

Хуки Husky делают это сами, но знать, что они запускают, полезно.

`pre-commit` линтит и форматирует только затронутый код (`nx affected`). Если в индексе одни `docs/`, шаг пропускается целиком.

`pre-push` собирает и тестирует затронутое, потом собирает решение целиком (`dotnet build DotnetVue3TemplateRu.slnx`) и сверяет OpenAPI-документ с закоммиченным. Полная сборка решения нужна потому, что `nx affected` собирает проекты по отдельности и не видит сам `.slnx`: битый состав или неверный путь в нём ловится только так.

Вручную то же самое:

```bash
dotnet build DotnetVue3TemplateRu.slnx
yarn nx run architecture-tests:test
yarn nx run integration-tests:test
yarn nx run web:test
yarn nx run-many --target=lint
yarn format:write
```

### Первый коммит в пустом репозитории

Хук `pre-push` сравнивает OpenAPI-спеку с её версией в `HEAD`. В репозитории без единого коммита `HEAD` не существует, `git diff HEAD` падает с "unknown revision", и хук не пропускает пуш - хотя ничего не сломано.

Поэтому самый первый коммит делается в обход хуков и обязан включать саму спеку:

```bash
git add .
git commit --no-verify -m "Первый коммит"
```

Второй и все последующие коммиты идут штатно, без флага: `HEAD` уже есть, и хуку есть с чем сравнивать. Если спека не попала в первый коммит, `pre-push` будет падать до тех пор, пока её не закоммитят.

## Контракт API коммитится

`apps/backend/DotnetVue3TemplateRu.Api/openapi/DotnetVue3TemplateRu.Api.json` - источник для генерации TS-клиента, и он лежит в git. Изменили контроллер - перегенерируйте и закоммитьте:

```bash
yarn nx run api-client:generate
```

Хук `pre-push` не пустит пуш, если спека разошлась. Документ обязан быть байт-в-байт одинаковым в любой среде сборки: dev-only эндпоинт, попавший в него, дрейфует между локальной сборкой и CI. Такое исключается на месте - `.ExcludeFromDescription()`.

## Тесты

Что и на каком уровне тестируется - [docs/spec/test-strategy.md](docs/spec/test-strategy.md). Коротко: основной уровень - интеграционные тесты через HTTP на настоящем PostgreSQL в контейнере; юнит-тесты пишутся там, где есть нетривиальная логика без HTTP.

Утверждайте полное значение, а не его отсутствие. `IsEqualTo` на всём объекте или снимок Verify говорят больше, чем проверка "не содержит" - последняя проходит и тогда, когда ответ тихо изменился.

## Документация

Решение с последствиями - новый ADR. Формат и нумерация - в [docs/adr/README.md](docs/adr/README.md).

Как реализовано - Diataxis-набор модуля в `docs/<area>/<module>/`, по одному файлу на жанр. Замысел и обоснования - `docs/spec/arch-design/`. Правило разделения - [ADR-0034](docs/adr/0034-documentation-lifecycle-layers.md).

Язык и подача - [docs/guides/documentation-style.md](docs/guides/documentation-style.md). Два правила, которые нарушают чаще всего: не переносить строки посреди предложения и использовать только ASCII-пунктуацию (дефис вместо тире, прямые кавычки).

## Добавить модуль или раздел

- Backend-модуль: [docs/guides/add-backend-module.md](docs/guides/add-backend-module.md), генератор - `scripts/add-new-module.sh`.
- Раздел фронтенда: [docs/guides/add-frontend-module.md](docs/guides/add-frontend-module.md).

Границы уровней фронтенда проверяет линт. После правки структуры убедитесь, что проверка действительно сработала бы: добавьте в фичу импорт соседней фичи, запустите `nx run web:lint` и посмотрите, что он падает с ошибкой `boundaries/element-types`; потом откатите импорт. Без такой пробы неверная настройка границ не видна: файл, не совпавший ни с одним шаблоном путей в `boundaries/elements`, плагин не относит ни к какому уровню и не проверяет вовсе, так что линт остаётся зелёным - ровно как при работающем правиле.
