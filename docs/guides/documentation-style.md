# Как писать документацию понятно

Правила языка и подачи для всей документации проекта. Отвечают на один вопрос: как написать так, чтобы документ понял человек, который не держит в голове терминологию автора.

Образец, на который равняются остальные документы, - [core-architecture.md](../spec/arch-design/core/core-architecture.md). Назначение временное: образцом станет design-документ первого предметного модуля, как только он появится. Жанры и их назначение описаны в [documentation-diataxis.md](documentation-diataxis.md), слои документации - в [ADR 0034](../adr/0034-documentation-lifecycle-layers.md); здесь - только про то, как написан текст внутри любого из них.

Понятность не означает поверхностности. Ни один технический факт, тип, маршрут или цифра не выбрасывается ради простоты изложения. Текст становится длиннее - обоснование, которое раньше жалось в скобку внутри предложения, разворачивается в отдельное предложение.

## 1. Требования к языку

Действуют во всех жанрах.

### 1.1. Термин объясняется там, где появляется

Проверка: уберите знание термина - предложение всё ещё что-то сообщает? Если нет, термин делает работу автора.

Было:

> Подпись асимметричная, открытые ключи приезжают по JWKS из discovery-документа и обновляются при ротации.

Стало:

> Провайдер подписывает токен своим закрытым ключом, а приложение проверяет подпись парным открытым. Открытые ключи приложение забирает у провайдера само, по адресу из его документа конфигурации, и подхватывает новые, когда провайдер меняет ключи. Такой набор открытых ключей называется JWKS.

Термин можно и сохранить - но после объяснения, как ярлык для уже понятой вещи: "приложение убирает повторы по идентификатору сообщения (дедупликация)".

### 1.2. Абзац - одна мысль

Ориентир 200-500 знаков, предел 800. Абзац длиннее предела разбивается на несколько или превращается в список.

Длинный абзац почти всегда означает, что в него сложили несколько независимых утверждений. Их и надо разложить.

### 1.3. Предложение - одна мысль

Не больше одной вставки в скобках. Точка с запятой, склеивающая два независимых правила, - сигнал поставить точку.

Было:

> Локализуемое поле не хранится только строками в таблице переводов (это дало бы join на каждом чтении), а дублируется инлайн в самой записи; на чтении берётся перевод культуры запроса, а при его отсутствии подставляется инлайн-значение (нет строки на культуру -> инлайн-дефолт, есть -> перевод).

Стало:

> Переводы сущности лежат отдельной таблицей, по строке на культуру. Значение культуры по умолчанию дополнительно хранится инлайн, в самой записи.
>
> На чтении проекция берёт перевод на культуре запроса. Если строки для этой культуры нет, подставляется инлайн-значение - поэтому текст никогда не приходит пустым.

### 1.4. Глагол вместо отглагольного существительного

| Было                                       | Стало                                               |
| ------------------------------------------ | --------------------------------------------------- |
| осуществляется резолвинг токена            | резолвер разбирает токен                            |
| производится валидация `CreateNoteCommand` | валидатор проверяет `CreateNoteCommand` до хендлера |
| отображение резолвится на чтении           | имя подставляется при чтении                        |
| происходит рассылка уведомлений            | уведомления расходятся по адресатам                 |

### 1.5. Выгода подкрепляется цифрой, сравнением или примером

"Быстрее", "дешевле", "проще", "дорого" без опоры - мнение, а не утверждение. Читатель не может ни проверить его, ни возразить.

Было:

> Архитектурные тесты быстрые и не требуют Docker, поэтому в CI их ставят перед интеграционными.

Стало:

> Архитектурные тесты читают собранные сборки и не поднимают ни приложение, ни базу: прогон занимает около 2 секунд. Интеграционным нужен контейнер PostgreSQL, и 26 тестов идут около минуты. Поэтому в CI архитектурные стоят первым барьером - нарушение правила зависимостей видно до того, как поднимется база.

Если цифры нет, годится конкретный пример последствия: "иначе при смене языка интерфейса пользователь теряет заполненную форму".

### 1.6. Определение говорит, чем вещь является

Отвергнутый вариант появляется только там, где сравниваются варианты, и описывается нейтрально.

| Было                                                | Стало                                                                                                                                     |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `IUserContext` - не список прав, а идентичность     | `IUserContext` несёт идентификатор текущего пользователя - значение claim `sub`                                                           |
| Хендлер - не класс с конструктором, а static-метод  | Хендлер - static-класс `*Handler` со static-методом `Handle`, и зависимости он получает параметрами этого метода                          |
| Шов идентичности - не отдельный проект, а интерфейс | Шов идентичности - это интерфейс `IUserContextResolver` в `Core.Application`, а его единственная реализация лежит в `Core.Infrastructure` |

Заголовок через отрицание не сообщает ничего читателю, который не знает обеих вещей.

### 1.7. Английское слово кириллицей - только для устоявшихся имён

Имена типов, файлов, маршрутов и библиотек остаются как есть, в бэктиках. Всё остальное переводится.

| Было                             | Стало                                                             |
| -------------------------------- | ----------------------------------------------------------------- |
| EF-плюминг                       | обвязка EF Core: контекст, репозитории, миграции                  |
| гейтятся атрибутом `[Authorize]` | закрыты атрибутом `[Authorize]`: без токена эндпоинт отвечает 401 |
| изоляция фич скоупится разделом  | изоляция фич действует в пределах раздела                         |
| БД не пухнет                     | база не растёт                                                    |
| pass-through ответов             | ответы читаются из хранилища и передаются дальше без изменений    |
| tokenless-приём                  | приём без токена                                                  |

## 2. Приёмы подачи

**Вводный абзац отвечает на вопрос читателя, а не описывает сам документ.**

Было: "Технический дизайн модуля `Core`: его место в системе, слои, ключевые решения и зависимости."

Стало: "Что попадает в `Core`, а что остаётся модулю, и почему ядро не знает о предметных модулях ничего. Здесь же - как идентичность пользователя доезжает от токена до обработчика и почему она едет полем команды, а не окружающим контекстом."

**Раздел открывается обещанием структуры.** "Задачу усложняют три обстоятельства", "Пять правил, к которым системы пришли независимо". Читатель понимает, сколько ему предстоит, и не теряется.

**Тезис жирным - законченное утверждение, а не заголовок-существительное.** Не "**Локализация.**", а "**Переводы хранятся отдельной таблицей, а значение языка по умолчанию лежит рядом с самой записью.**" Дальше обычный текст раскрывает тезис.

**Возражение читателя проговаривается вслух и снимается.** "Пятое правило вызывает законный вопрос: список приходит одним запросом, значит соединить всё равно придётся. Верно, вопрос лишь в том, где это происходит."

**Причина называется прямо.** Не "здесь это не подходит", а "различие, из-за которого приём подходит фоновой рассылке и не подходит здесь, - в том, что ответ нужен в том же запросе".

## 3. Структура по жанрам

Требования к языку общие для всех, порядок разделов - свой.

| Жанр                                  | Порядок разделов                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Проектный дизайн (`spec/arch-design`) | задача обычными словами -> что мешает -> варианты -> выбор с обоснованием -> механизм -> порядок работ |
| ADR (`adr`)                           | проблема -> варианты -> решение -> последствия                                                         |
| Справочник (`reference`)              | таблицы и перечни; термины раскрываются один раз во вводном разделе                                    |
| Объяснение (`explanation`)            | почему устроено именно так; каждое "почему" - отдельный короткий раздел                                |
| Инструкция (`how-to`, `tutorial`)     | шаги, каждый с проверкой результата                                                                    |

## 4. Общие требования к оформлению

- Обезличенный голос: требования как факты проекта, без обращения к читателю и без следов обсуждения.
- Только ASCII, кроме кириллицы текста. Тире - одиночный дефис, кавычки - прямые двойные.
- Предложение на одной строке, без переносов по ширине колонки.
- Таблицы выровнены, у блоков кода указан язык.

## 5. Проверка перед сдачей

1. Самый длинный абзац - не больше 800 знаков.
2. Нет предложения, которое нельзя прочесть вслух на одном дыхании.
3. Каждый термин объяснён при первом появлении.
4. У каждого утверждения о выгоде есть цифра, сравнение или пример.
5. Ни один заголовок не определяет предмет через отрицание.
6. Английские слова кириллицей - только имена из кода.

Первый и второй пункты считаются скриптом: длина абзацев и предложений. Ориентиры сняты с образца по его абзацам прозы (без заголовков, списков, таблиц и блоков кода) - 16 абзацев, средний 306 знаков, самый длинный 446, самое длинное предложение 34 слова.
