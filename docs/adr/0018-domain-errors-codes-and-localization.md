# ADR: Доменные ошибки, коды ошибок и локализация сообщений

- Статус: Принято
- Дата: 2026-07-05
- Контекст: монорепозиторий DotnetVue3TemplateRu, backend (.NET 10, Clean Architecture + CQRS на Wolverine), единый формат ошибок RFC 9457 (ADR-0017), валидация FluentValidation (ADR-0019), локализация запроса RequestLocalization (ru/en/kk)

## Контекст

Приложение мультиязычное, и ошибки нужны как часть контракта, а не как случайные строки. Базовый шаблон этого не давал: доменные инварианты бросали голый `ArgumentException` с захардкоженным текстом, валидаторы FluentValidation дублировали те же проверки со своими текстами, а `GlobalExceptionHandler` отдавал ProblemDetails с английскими литералами - при том что механизм культуры запроса уже был. Требования к решению:

- **Локализация текстов ошибок** по текущей культуре запроса (та же, что у контента, - `CultureInfo.CurrentCulture` из RequestLocalization).
- **Стабильный код ошибки** на каждую ошибку, чтобы фронтенд-клиент (Orval) ветвился по коду, а не по тексту.
- **Единый источник кода и текста** между доменным инвариантом и валидатором команды: одна и та же проверка не должна расходиться в двух местах текстами и описаниями.
- **Один список всех ошибок** (код + сообщение) для обзора и стража полноты переводов.

## Решение

**1. Сигнал ошибки - исключения; доменный `DomainException` с кодом.** Базовый `DomainException` (в `Core.Domain/Errors/`) несёт `ErrorCode` (стабильный код) и `Args` (параметры плейсхолдеров). Доменные инварианты бросают его; текст не хранится. `NotFoundException` (Application) устроен так же - несёт `ErrorCode` + `Args` и локализуется по коду на границе (ответ 404); `FluentValidation.ValidationException` остаётся. Сквозные ответы обработчика без собственного исключения - конфликт оптимистичной блокировки (409, `DbUpdateConcurrencyException`) и непредвиденная/прочая ошибка (500 и 400-fallback) - тоже локализуются по фиксированным кодам `common.*`. Клиенту в проде не уходит английский технический текст ошибки. Хендлеры Wolverine возвращают DTO напрямую - исключения не проходят через сигнатуры.

**2. Гибрид value object / агрегат.** Переиспользуемый leaf-VO (напр. `Email`, `Bin` в shared kernel) валидирует формат фабрикой, возвращающей `Result<T>` (в `Core.Domain/Errors/`) с обезличенным кодом при провале - VO не знает контекста применения. Агрегат-композитор разворачивает результат и бросает `DomainException` с контекстным кодом (`employee.email.invalid`, а не общий `email.invalid`): контекст живёт в коде, который выбирает агрегат. Собственные инварианты агрегата бросают `DomainException` напрямую.

**3. Код ошибки - C#-константы в каталоге `ErrorCodes`.** Namespaced-нотация `модуль.поле.правило` (`note.text.required`, `schedule.time_range.start_after_end`). Каталог живёт в Domain-слое своего модуля (общий нижний слой: на него ссылаются и домен, и Application). Это машинный "список кодов", компайл-тайм-безопасный: код упоминается константой, а не магической строкой.

**4. Единый предикат правила.** Проверка, общая для домена и валидатора, живёт один раз - доменной спецификацией/guard-функцией над примитивами (или внутри `VO`-фабрики), которую вызывают и агрегат, и валидатор FluentValidation. Оба ссылаются на один код через `WithErrorCode(...)`. Доменный инвариант - источник истины и живёт в домене (ADR-0008); FluentValidation на границе команды зеркалит его тем же кодом, даёт словарь `errors` по полям и fail-fast до хендлера, но не является единственным местом правила. Итог: предикат - один раз, код - один раз, текст - один раз.

**5. Тексты - resx + `IStringLocalizer`, резолв в одной точке на границе.** Домен и валидаторы отдают только код (+параметры), не текст. Единственная точка резолва "код + культура + параметры -> локализованный текст" - `GlobalExceptionHandler`, для всех путей: доменных исключений, `NotFoundException` (404), конфликта блокировки (409) и непредвиденной ошибки (500), а также словаря `errors` валидации. Тексты - в `apps/backend/DotnetVue3TemplateRu.Api/Resources/Localization/ErrorMessages.*.resx` (ключ = код ошибки; нейтральная культура несёт русский текст, плюс `en` и `kk`). Плейсхолдеры валидатора (`{MaxLength}`) подставляются из значений FluentValidation, доменные (`{0}`) - из `Args`. Домен и Application остаются без зависимости от локализации.

**6. `RequestLocalization` выше `UseExceptionHandler` в конвейере.** Обработчик исключений оборачивает нижние middleware; культура, выставленная ниже по стеку, ему не видна - значение `AsyncLocal`, установленное в более глубоком async-кадре, не всплывает наверх при развёртке стека исключения. Поэтому `UseRequestLocalization()` идёт первым, чтобы культура была установлена к моменту работы обработчика.

**7. ProblemDetails несёт код.** Доменная ошибка, `NotFoundException` (404), конфликт блокировки (409) и непредвиденная/прочая ошибка (500/400-fallback) кладут `errorCode`; ошибка валидации - словарь `errorCodes` (код на каждое поле) рядом со словарём `errors` (локализованные тексты). Клиент ветвится по коду.

**8. Страж полноты ("один список").** Тест обходит рефлексией константы `ErrorCodes` и проверяет по каждой поддерживаемой культуре без фолбэка, что у кода есть ресурс, - пропущенный перевод не маскируется откатом к нейтральному.

## Почему не альтернативы

**`Result<T>` в сигнатурах хендлеров вместо исключений.** Функциональный результат вирален по всему стеку и ломает конвенцию Wolverine, где хендлер возвращает DTO напрямую. `Result` применяется точечно - только в фабриках переиспользуемых VO, где нужен возврат обезличенного провала в агрегат; на уровне бизнес-операций сигнал - исключение с кодом.

**Текст сообщения в каждом слое (в валидаторе и в домене).** Расходится между слоями и дублирует описания. Код в обоих слоях + резолв текста по коду в одной точке даёт единый источник и убирает дублирование текста, оставляя каждому слою свою роль.

**Локализация текстов на фронтенде по коду.** Требует контракта параметров на каждый код и уводит "список сообщений" с бэкенда, тогда как ошибки нужны локализованными и не-UI потребителям (логи, другие сервисы). Бэкенд отдаёт код и локализованный текст; фронтенд при необходимости дополнительно ветвится по коду.

**Тексты ошибок в таблице переводов БД (как контент сущностей, ADR по локализации).** Тексты ошибок - статические строки, авторские при разработке, а не пользовательские данные; их место - ресурсы под контролем версий и сборки, а не строки БД.

## Плюсы

- Единый источник: предикат, код и текст ошибки - по одному разу; домен и валидатор не расходятся.
- Тексты локализованы по культуре запроса единообразно с контентом; домен и Application свободны от зависимости на локализацию (резолв только на границе).
- Стабильные коды в ProblemDetails -> клиент ветвится по коду, не по тексту.
- "Один список" кодов - компайл-тайм-константы; страж гарантирует перевод на каждую культуру.

## Минусы

- Предикат правила, общий для домена и валидатора, выражается в двух вызовах (домен + FluentValidation) - но через общую функцию и один код.
- Тексты в resx требуют рекомпиляции/пересборки сателлитов при изменении; перевод редактируется не на лету.
- Порядок конвейера чувствителен: `RequestLocalization` обязан стоять выше `UseExceptionHandler`.

## Последствия

- Доменные инварианты бросают `DomainException` с кодом из каталога `ErrorCodes` своего модуля; голый `ArgumentException` в домене не используется (маппинг `ArgumentException -> 400` в `GlobalExceptionHandler` остаётся как защита для прочих/BCL-случаев).
- `NotFoundException` (Application) несёт код из каталога `ErrorCodes` (напр. `note.not_found`); `GlobalExceptionHandler` локализует Detail и кладёт `errorCode` (404). Конфликт оптимистичной блокировки (409), непредвиденная/прочая ошибка (500 и 400-fallback) и отказ ограничителя частоты (429) локализуются по сквозным кодам `common.*` (`concurrency_conflict`, `unexpected_error`, `bad_request`, `rate_limit_exceeded`) в каталоге Core. В проде клиенту уходит только обобщённое локализованное сообщение; в dev fallback показывает исходный текст исключения для диагностики. Английский текст ошибки клиенту в проде не отдаётся. Title в ProblemDetails - технический ярлык типа (RFC 9457), локализуется только Detail.
- Валидатор команды несёт код через `WithErrorCode(...)` из того же каталога; текст в валидаторе не задаётся - резолвится на границе.
- Новый код ошибки = константа в `ErrorCodes` + запись в `ErrorMessages.resx` (нейтральный, русский), `ErrorMessages.en.resx` и `ErrorMessages.kk.resx` (ключ = код); страж полноты падает, если перевод забыт.
- Тексты ошибок отдаются локализованными; ProblemDetails несёт `errorCode`/`errorCodes`. Интеграционные тесты проверяют локализованный текст и код по `Accept-Language` (`ErrorLocalizationEndpointTests`), unit-страж - полноту переводов (`ErrorCodesLocalizationTests`).
- Модуль объявляет свой каталог `ErrorCodes` в собственном Domain-слое; тексты его кодов добавляются в общий `ErrorMessages.*.resx`.
