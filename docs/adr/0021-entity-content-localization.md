# ADR: Локализация контента сущностей (таблица переводов)

- Статус: Принято
- Дата: 2026-08-11
- Контекст: модульный монолит DotnetVue3TemplateRu, backend (.NET 10, Clean Architecture + CQRS на Wolverine), EF Core + PostgreSQL (ADR-0007), локализация запроса RequestLocalization (ru/en/kk), локализация текстов ошибок через resx (ADR-0018)

## Контекст

Интерфейс многоязычный (русский, английский, казахский), и часть текстовых полей сущностей локализуема: названия, описания, значения справочников. Это данные - их вводит пользователь или они приходят готовым набором локалей, а не задаются автором при разработке. Их нужно хранить так, чтобы:

- **Поддержать произвольное число языков без изменения схемы БД** - добавление языка не должно требовать миграции.
- **Переиспользовать механизм между модулями** - каждый модуль добавляет только свой набор локализуемых полей, а не свою реализацию хранения и маппинга.
- **Разрешать язык на чтении** по текущей культуре запроса, единообразно с остальной локализацией (та же `CultureInfo.CurrentCulture` из RequestLocalization).

Это отдельная задача от локализации текстов ошибок (ADR-0018). Тексты ошибок - статические авторские строки, их место в ресурсах под контролем версий и сборки (resx). Контент сущностей - пользовательские и внешние данные, их место в БД. Поэтому у них разные механизмы.

## Решение

**Локализуемые поля хранятся в дочерней таблице переводов (translation-table); значение культуры по умолчанию дублируется инлайн в главной таблице; язык разрешается на чтении. Базовый тип и EF-маппинг переиспользуемы (ядро), модуль добавляет только свой тип перевода.**

**1. Модель хранения - таблица переводов + инлайн-дефолт.** У локализуемой сущности две таблицы. Дочерняя `<Entity>Localizations` хранит значения для всех культур, включая дефолтную, - по строке на пару (сущность, культура); колонки `Id` (PK), `RelationId` (FK на сущность), `Culture` (`CultureInfo.Name`) и сами локализуемые поля. Главная таблица дополнительно несёт значение дефолтной культуры прямо в колонке - это денормализованный дефолт: доступен без join и служит фолбэком для культур без перевода. Одна строка переводов = один язык одной сущности; все локализуемые поля этой сущности лежат в этой строке.

**2. Переиспользуемое ядро.** Базовый `LocalizationEntity` (`Id`/`RelationId`/`Culture`) - в `Core.Domain/Localization/`. Модуль объявляет свой тип перевода, наследуя его и добавляя локализуемые поля (`NoteLocalization : LocalizationEntity` с `Text`). Локализуемая сущность несёт значение дефолтной культуры инлайн, коллекцию переводов `IReadOnlyCollection<TLocalization> Localizations` и раскладывает входящие локали в строки при создании/обновлении. Домен зависит только от `Core.Domain`, не от инфраструктуры.

**3. Единый EF-маппинг.** Универсальный хелпер `ConfigureLocalization<TEntity, TLocalization>` (в `Core.Infrastructure/Persistence/`) ставит таблицу `<Entity>Localizations` с собственным `Id` PK, внешний ключ `RelationId` с каскадным удалением, уникальный индекс `(RelationId, Culture)` и ограничение длины `Culture`. Одинаково для любой локализуемой сущности; длины самих локализуемых полей задаются рядом отдельно.

**4. Культура - из запроса.** Текущая культура берётся штатным `RequestLocalizationMiddleware` (провайдеры query-string, cookie, `Accept-Language`; `DefaultCulture`/`SupportedCultures` из конфигурации) в `CultureInfo.CurrentCulture`. Значение `AsyncLocal`, поэтому доступно и Wolverine-хендлерам, исполняемым в отдельном DI-скоупе.

**5. Разрешение на чтении.** Локализуемое поле разрешается в проекции квери-репозитория: перевод текущей культуры, при его отсутствии - значение по умолчанию из главной таблицы (`Localizations.Where(l => l.Culture == culture).Select(...).FirstOrDefault() ?? inline`). Фронту отдаётся уже разрешённая строка - выбор культуры на чтении, не в контракте и не на персистентности.

**6. Запись раскладывает все локали.** Значения из внешнего источника, приходящие всеми локалями сразу, раскладываются при сохранении: каждая культура - строка в `Localizations` (включая дефолтную), значение дефолтной культуры дублируется в инлайн-поле. Пользовательский ввод пишется так же: перевод на культуру - строка в `<Entity>Localizations` (для дефолтной культуры - синхронно и в инлайн-поле). Дефолтная культура берётся из `CultureOptions.DefaultCulture`.

**7. Форма поля в контракте - `LocalizedText`, по полю.** Локализуемое поле в DTO контракта записи - это карта `culture -> значение` (`IReadOnlyDictionary<string, string>`, ключ - `CultureInfo.Name`); эта форма обозначается как `LocalizedText`. Каждое локализуемое поле - отдельное именованное свойство: сущность с несколькими локализуемыми полями несёт несколько таких карт (например, `name` и `description`), и покрытие культур у полей независимо (у `name` могут быть ru-RU и kk-KZ, у `description` - только ru-RU). Контракт записи принимает все локали поля сразу и раскладывает их в строки перевода (п. 6). На чтении форма зависит от назначения контракта: контракт редактирования отдаёт ту же карту всех культур (чтобы редактор показал каждый язык отдельно), контракт отображения - уже разрешённую по культуре строку (п. 5).

**8. Добавление языка - данными.** Зарегистрировать культуру в `SupportedCultures` конфигурации и писать строки перевода в `<Entity>Localizations`. Изменение схемы БД не требуется.

## Почему не альтернативы

**Колонка на язык (`Name_ru`, `Name_kk`).** Каждый новый язык - миграция и правка всех проекций; число языков зашивается в схему. Таблица переводов добавляет язык строкой.

**JSON-колонка с картой культура -> значение.** Нет реляционной целостности и уникальности перевода на уровне БД, сложнее индексировать и фильтровать по конкретному языку, поведение зависит от версии движка. Таблица переводов даёт нормальные FK, уникальный индекс `(RelationId, Culture)` и прямую фильтрацию по культуре.

**Внешняя i18n-библиотека для локализации сущностей.** Тянет зависимость и её модель хранения ради того, что покрывается одним базовым типом и одним EF-хелпером. Собственное минимальное ядро остаётся под контролем проекта и не навязывает чужих соглашений.

**Разрешение культуры на персистентности (хранить одну строку выбранной культуры).** Теряет прочие переводы: в БД должны лежать все локали, а выбор языка - дешёвая операция чтения. Поэтому культура выбирается в проекции, а не при сохранении.

**Тексты ошибок в той же таблице переводов.** Тексты ошибок - статические авторские строки, а не данные; их место в resx под контролем сборки (ADR-0018). Таблица переводов - только для контента сущностей.

## Плюсы

- Произвольное число языков без изменения схемы БД: добавить язык - добавить строки.
- Один базовый тип и один EF-маппинг на все сущности; модуль добавляет лишь свой тип перевода.
- Денормализованный инлайн-дефолт: доступ к дефолту без join и фолбэк для культур без перевода.
- Язык выбирается на чтении единообразно с остальной локализацией; домен свободен от зависимости на инфраструктуру.
- Реляционная целостность перевода: FK с каскадом и уникальность `(RelationId, Culture)` на уровне БД.

## Минусы

- Значение дефолтной культуры хранится дважды (инлайн и строкой перевода) - запись обязана держать их синхронными.
- Чтение локализуемого поля - коррелированный подзапрос к таблице переводов (проекция с фолбэком), а не простая колонка.
- Каждое локализуемое поле живёт в строке перевода; набор полей перевода фиксируется типом `<Entity>Localization`.

## Последствия

- Демо-сущность `Note` - первый носитель механизма: `Text` локализован (`NoteLocalization`, таблица `NoteLocalizations`), создание принимает все локали сразу, чтение разрешает текст по культуре запроса. См. [Guide: локализация контента сущности](../guides/entity-localization.md).
- Модуль с локализуемым контентом объявляет свой `<Entity>Localization : LocalizationEntity` в своём Domain-слое и вызывает `ConfigureLocalization<Entity, EntityLocalization>` в своём `DbContext`; таблица переводов попадает в миграции модуля.
- Локализация текстов ошибок остаётся на resx + `IStringLocalizer` (ADR-0018) - это другой механизм для статических строк.
- Новый язык подключается регистрацией культуры в `SupportedCultures` и записью строк перевода, без миграции схемы.
