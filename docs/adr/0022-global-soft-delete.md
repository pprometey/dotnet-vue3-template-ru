# ADR: Глобальное мягкое удаление

- Статус: Принято
- Дата: 2026-08-11
- Контекст: EF Core во всех модулях; закрытые записи ссылаются на пользователей и на значения справочников в тех формулировках, что действовали тогда

## Контекст

Политика проекта - жёстких удалений ключевых сущностей нет: строка не исчезает физически, а помечается удалённой и скрывается из обычных запросов. Причина не в абстрактной ценности истории, а в том, что закрытые записи остаются доступными для просмотра и ссылаются на другие строки в тех формулировках, что действовали на момент записи.

Отсюда два требования, которые обычное удаление выполнить не может. Пользователь, выведенный из работы, обязан исчезнуть из текущих списков и перестать получать задачи, но его прошлые записи должны остаться читаемыми. Значение справочника, выведенное из оборота, не должно предлагаться в новых документах, но закрытый документ без него развалится - там на него есть ссылка.

Есть и третий случай, который решает та же пометка: пользователь, ушедший и вернувшийся, должен ожить со своей историей, а не завестись дублем.

Механизм нужен переиспользуемый (не по одной сущности вручную) и единообразный: пометка удаления, автоматическое скрытие из запросов, и возможность точечно снять скрытие там, где нужно увидеть удалённые строки (просмотр истории, сверка с внешним источником, оживление).

## Решение

**Мягкое удаление - общий механизм в Core: доменный маркер + интерцептор сохранения + модель-конвенция query-filter.**

- `Core.Domain/SeedWork/ISoftDeletable` - маркер с `DateTimeOffset? DeletedAtUtc`. Сущность реализует его и несёт доменные операции `Deactivate()` / `Reactivate()` (у EF нет перехода "снять удаление", оживление - явная доменная операция). Инфра-атрибутов на домене нет; сам механизм - в Infrastructure.
- `Core.Infrastructure/Persistence/SoftDeleteSaveChangesInterceptor` - на сохранении переводит `EntityState.Deleted` для `ISoftDeletable` в `Modified` и штампует `DeletedAtUtc`, не трогая остальные значения (в т.ч. `OriginalValues` rowversion, чтобы оптимистичная блокировка `UPDATE ... WHERE Version = original` продолжала работать). Если в проекте появится интерцептор аудита, этот регистрируется ПЕРЕД ним - иначе мягкое удаление попало бы в журнал как физическое; в такой очерёдности аудит видит его как `Update` с изменением `DeletedAtUtc` (след "кто и когда деактивировал").
- `Core.Infrastructure/Persistence/ModelBuilderSoftDeleteExtensions.ApplySoftDeleteConvention()` - в конце `OnModelCreating` для каждого mapped-типа, реализующего `ISoftDeletable`, вешает query-filter `e => e.DeletedAtUtc == null` и индекс на `DeletedAtUtc`.
- Запросам, которым нужно ВИДЕТЬ мягко удалённые строки (сверка с внешним источником, оживление вернувшихся), фильтр снимается через `IgnoreQueryFilters()` - иначе удалённая строка не найдётся, и get-or-create вставит дубль в обход уникального индекса.

Политика по сущностям задаётся тем, реализует ли тип `ISoftDeletable`. Маркер получают сущности, на которые ссылаются закрытые записи: пользователь и значение справочника. Не получают его append-only записи (журналы событий, отправленные уведомления) и таблицы переводов: журнал по определению не удаляют, а перевод живёт и умирает вместе со своей строкой-владельцем через каскад, поэтому второй фильтр на нём только мешал бы.

## Почему не альтернативы

**Физическое удаление + аудит.** Аудит хранит след, но сама строка и её связанные данные (заполненный профиль пользователя) исчезают; оживление вернувшегося пользователя невозможно без пересоздания, а пересоздание рвёт ссылки и историю. Мягкое удаление сохраняет и строку, и профиль.

**Ручной query-filter и пометка на каждой сущности отдельно.** Работает, но дублирует один и тот же код по сущностям и легко забывается на новой; конвенция по маркеру навешивает фильтр и индекс единообразно и автоматически.

**Явное поле-статус (Active/Deleted) вместо интерцептора.** Требует, чтобы каждый код-путь помнил проставлять статус вместо `Remove`; интерцептор ловит любой `Remove` на `ISoftDeletable` централизованно (защитный слой), а доменные `Deactivate/Reactivate` дают явную семантику там, где удаление - часть бизнес-логики.

## Плюсы

- Единый переиспользуемый механизм: новая сущность становится мягко удаляемой одним маркером, фильтр и индекс навешиваются конвенцией.
- Сохранение данных: выбывший пользователь исчезает из текущих списков, но его запись и профиль остаются - оживление при возврате без дубля.
- Совместимость с оптимистичной блокировкой (rowversion не сбивается) и с аудитом (удаление видно как Update с автором).

## Минусы

- Легко забыть `IgnoreQueryFilters()` там, где нужны удалённые строки (get-or-create, сверка) - тогда оживление молча ломается; требует внимания на таких путях.
- Уникальные индексы охватывают и мягко удалённые строки, поэтому повторная вставка "того же" ключа конфликтует - оживление обязано идти через `Reactivate`, а не через новый insert.
- EF предупреждает про query-filter на обязательной навигации между двумя мягко удаляемыми сущностями (например, строка документа и справочное значение, на которое она ссылается) - предупреждение осознанно принимается, оба фильтра значат одно и то же.

## Последствия

- Core: `ISoftDeletable`, `SoftDeleteSaveChangesInterceptor`, `ApplySoftDeleteConvention` - переиспользуемы всеми модулями.
- Кандидаты на маркер в предметных модулях: пользователь, значение справочника, сущность-владелец. Решение принимается по сущности: реализует она `ISoftDeletable` или нет.
- Пока ни одна сущность шаблона маркер не реализует, механизм молчит: конвенция обходит модель и не находит ничего, интерцептор не срабатывает. Это осознанно - три файла в Core стоят дешевле, чем ретроспективное введение мягкого удаления поверх уже накопленных данных.
- Интерцептор регистрируется при конфигурации `DbContext`; в интеграционных тестах тест-хост повторяет ту же очерёдность.
