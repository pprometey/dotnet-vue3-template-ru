# ADR: Использование Nx для управления монорепозиторием

- Статус: Принято
- Дата: 2026-08-11
- Контекст: монорепозиторий DotnetVue3TemplateRu (frontend на Vue + backend на .NET/Aspire)

## Контекст

DotnetVue3TemplateRu - это не один проект, а набор связанных приложений и
библиотек, живущих в одном репозитории:

- frontend: `apps/frontend/web` (SPA на Vue 3, Vite, Storybook) и
  библиотека `libs/frontend/api-client`;
- backend: `apps/backend/DotnetVue3TemplateRu.Api`, слои
  `libs/backend/core/DotnetVue3TemplateRu.Core.Domain`, `...Core.Application`,
  `...Core.Infrastructure` (.NET);
- оркестрация: `aspire-apphost` (AppHost на TypeScript, ADR 0005) поднимает всё вместе.

Между этими частями есть зависимости: приложения опираются на
библиотеки, библиотеки - друг на друга, а `api-client` генерируется из
backend-контракта (OpenAPI). Без единого инструмента это порождает
типовые проблемы монорепозитория:

- нужно вручную знать, что и в каком порядке собирать;
- CI пересобирает и перетестирует всё подряд, даже при изменении
  одного пакета;
- нет единого способа описать таски (`build`, `lint`, `test`) для
  разнородных стеков (Node и .NET одновременно).

## Решение

Используем Nx как систему сборки и управления монорепозиторием.
Конфигурация - в `nx.json`, у каждого проекта есть свой `project.json`.
Nx интегрирован с Yarn workspaces (см. ADR по Yarn) и оркеструет таски
поверх обоих стеков - и frontend, и backend.

Ключевые элементы текущей настройки (`nx.json`):

- `targetDefaults` с `cache: true` для `build`, `lint`, `test` -
  включено кэширование результатов;
- `dependsOn: ["^build"]` для `build` - Nx сам строит зависимости в
  правильном порядке;
- `namedInputs` (`default`, `production`) - тесты и сторибуки исключены
  из production-входов, чтобы их изменение не инвалидировало build-кэш;
- `defaultBase: "main"` - база для команд `nx affected`.

Скрипты в `package.json` уже построены вокруг Nx:
`nx affected --target=lint`, `nx affected --target=build`,
`nx affected --target=test`, `nx run aspire-host:serve`.

## Структура проекта

Репозиторий устроен как Nx-монорепо с единым деревом для обоих стеков.
Верхний уровень:

- `apps/` - запускаемые приложения и точки деплоя (frontend, backend,
  Aspire-host); подробно - в разделе ниже.
- `libs/` - переиспользуемые библиотеки (frontend и backend); подробно -
  в разделе ниже.
- `tests/` - тесты, не привязанные к одному проекту, например
  `tests/DotnetVue3TemplateRu.IntegrationTests` (интеграционные тесты backend).
- `docs/` - документация: `docs/adr` (этот и другие ADR),
  `docs/guides`, `docs/spec`.
- `scripts/` - вспомогательные скрипты разработки и CI.
- конфигурация в корне: `nx.json` (Nx), `package.json` + `yarn.lock`
  (Yarn workspaces и скрипты), `tsconfig.base.json` (общий TS-конфиг),
  `eslint.config.mjs` (линт), `DotnetVue3TemplateRu.slnx` (.NET solution),
  `aspire.config.json` (Aspire).

Фронтенд-часть асимметрична backend-у: приложение одно
(`apps/frontend/web`), а в `libs/frontend/` лежит единственная
библиотека `api-client`. Она библиотека не ради переиспользования
интерфейса, а потому что генерируется из другого источника - схемы
OpenAPI - и имеет свой цикл жизни: её нельзя править руками, тогда как
код приложения править можно (ADR 0027).

Ключевые идеи раскладки:

- Один репозиторий, два стека. Vue-frontend и .NET-backend лежат
  рядом и связаны через граф Nx, а не через отдельные репозитории и
  ручную синхронизацию версий.
- Зеркальные подпапки `frontend`/`backend`. И внутри `apps`, и внутри
  `libs` код делится на `frontend` и `backend`, поэтому одинаковая
  логика поиска работает для обеих частей.
- Код отдельно от конфигурации и документации. Приложения и
  библиотеки - в `apps`/`libs`; всё, что их обслуживает (конфиги,
  скрипты, доки, тесты), - на верхнем уровне и в выделенных папках.

## Структура `apps` и `libs`

Репозиторий разбит на две верхнеуровневые папки - `apps` и `libs`.
Это рекомендованная Nx раскладка, и здесь она решает конкретные задачи.

- `apps` - то, что разворачивается и запускается само по себе:
  `apps/frontend/web` (Vue-приложение), `apps/backend/DotnetVue3TemplateRu.Api`
  (.NET API), `aspire-apphost` (Aspire-оркестратор). Это точки входа
  и единицы деплоя.
- `libs` - переиспользуемый код, который сам по себе не разворачивается,
  а подключается приложениями и другими библиотеками:
  `libs/frontend/api-client`,
  `libs/backend/core/DotnetVue3TemplateRu.Core.Domain`, `...Core.Application`,
  `...Core.Infrastructure`.

Почему так удобно и зачем это нужно:

1. Чёткое разделение деплоя и логики. Сразу видно, что является
   запускаемым артефактом (`apps`), а что - библиотекой (`libs`).
   Приложение остаётся тонким: оно собирает вместе библиотеки, а не
   несёт в себе всю бизнес-логику.
2. Направление зависимостей. Зависимости идут от `apps` к `libs` и
   между `libs`, но не в обратную сторону. Это удерживает архитектуру
   от циклов: бизнес-логика (например, `Core.Domain`) не знает о
   конкретном приложении, которое её использует.
3. Переиспользование. Одну библиотеку могут использовать несколько
   приложений (или несколько библиотек). Например, `api-client` -
   это `lib`, на которую опирается SPA `web`; при появлении второго
   фронта она переиспользуется без копирования.
4. Тонкая гранулярность для `affected` и кэша. Чем мельче и
   осмысленнее разбиение на `libs`, тем точнее Nx понимает, что
   затронуто изменением, и тем меньше пересобирает и перетестирует.
   Слои backend (`Domain`, `Application`, `Infrastructure`) вынесены в
   отдельные `libs` именно поэтому.
5. Единая раскладка для двух стеков. И frontend, и backend живут по
   одному правилу `apps` против `libs` (с подпапками `frontend` и
   `backend`). Разработчику не нужно держать в голове разные структуры
   для разных частей репозитория.
6. Предсказуемость для новых участников. Раскладка `apps`/`libs` -
   это конвенция Nx; знакомый с Nx разработчик сразу понимает, где
   искать приложения, а где - общий код.

Эта структура напрямую усиливает выгоды от Nx из следующего раздела:
граф зависимостей, `affected`-команды и кэширование работают тем
лучше, чем чище разделение на приложения и библиотеки.

## Зачем Nx именно здесь

1. Граф зависимостей. Nx строит граф проектов и знает, что от чего
   зависит. Это убирает ручную координацию порядка сборки между
   frontend, backend и общими библиотеками.
2. `affected`-команды. Nx определяет, какие проекты затронуты
   изменением относительно `main`, и собирает/тестирует только их.
   Для монорепо с двумя стеками это кардинально ускоряет CI.
3. Кэширование. Повторный `build`/`lint`/`test` с теми же входами
   берётся из кэша вместо повторного выполнения. Локально и в CI это
   экономит минуты на каждом прогоне.
4. Единый интерфейс задач. Один и тот же набор команд (`build`, `lint`,
   `test`, `serve`) работает и для Vue-пакетов, и для .NET-проектов, и
   для Aspire-хоста. Разработчику не нужно помнить разные команды для
   разных частей.
5. Масштабируемость. По мере роста сервиса добавление нового приложения
   или библиотеки - это новый `project.json`, а не переписывание
   пайплайнов сборки.
6. Генерация API-клиента. Сама генерация фронтового клиента из
   backend-эндпоинтов оформлена как Nx-таргет (`api-client:generate`),
   поэтому она встроена в общий граф и кэширование наравне с остальными
   тасками (подробнее - в разделе ниже).

## Генерация API-клиента из backend-эндпоинтов

Фронтенд не пишет клиентский слой к API руками. Библиотека
`libs/frontend/api-client` генерируется из контракта backend:

1. собирается backend (`dotnet build` для `DotnetVue3TemplateRu.Api`), в
   результате чего формируется OpenAPI-спека
   (`apps/backend/.../openapi/DotnetVue3TemplateRu.Api.json`);
2. Orval по этой спеке (`orval.config.ts`) генерирует типизированный
   клиент: модели, vue-query хуки (репозитории запросов) поверх axios.

Это и есть "генерация репозиториев фронта на базе эндпоинтов backend":
для каждого тега API получается готовый набор хуков/функций доступа к
данным, синхронный с реальным контрактом сервера.

Почему здесь нужен Nx:

- Порядок шагов. Генерация требует сначала собрать backend, потом
  запустить Orval. В `project.json` это описано одним таргетом
  `generate` с `parallel: false`, так что шаги всегда идут по порядку.
- Единая точка запуска. Команда `nx run api-client:generate` (скрипт
  `generate:api-client` в `package.json`) одинаково работает локально и
  в CI - не нужно вручную помнить про `dotnet build` перед Orval.
- Граф зависимостей. Сгенерированный `api-client` - обычный проект Nx,
  от которого зависит фронтенд. Nx учитывает эту связь при сборке,
  линте и `affected`-командах: изменение контракта корректно
  протягивается по графу к зависимым пакетам.
- Согласованность стеков. Шаг генерации соединяет .NET-backend и
  Node-frontend в одном таске - ровно та разнородность, ради которой
  и нужен единый оркестратор.

## Почему Nx - индустриальный стандарт

Nx - один из самых распространённых инструментов для монорепозиториев
в профессиональной разработке. Его выбирают команды, которым нужно
держать много связанных пакетов в одном репозитории с быстрым и
предсказуемым CI. Причины популярности:

- зрелая модель графа проектов и `affected`-вычислений;
- кэширование (локальное и удалённое через Nx Cloud);
- богатая экосистема плагинов и генераторов;
- активная поддержка и большое сообщество.

Для команды это означает понятный, документированный и переносимый
подход: новые разработчики, знакомые с Nx по другим проектам, быстро
включаются в работу.

## Плюсы и минусы

### Nx

Плюсы:

- граф зависимостей и автоматический порядок сборки;
- `affected`-команды - собираем/тестируем только изменённое;
- кэширование результатов тасков (локально и в Nx Cloud);
- единый интерфейс задач поверх разных стеков (Node и .NET);
- генераторы и плагины ускоряют создание новых проектов;
- хорошо масштабируется при росте числа пакетов;
- распространённый инструмент - низкий порог входа для опытных команд.

Минусы:

- дополнительный слой абстракции и своя терминология (targets, inputs,
  named inputs) - нужно потратить время на изучение;
- конфигурация (`nx.json` + `project.json`) добавляет файлов и правил;
- кэш требует корректно описанных входов, иначе возможны ложные
  попадания/промахи;
- удалённый кэш (Nx Cloud) - отдельный сервис со своей моделью
  стоимости и приватности;
- для совсем маленького проекта Nx может оказаться избыточным.

### Альтернатива: без Nx (скрипты + ручная координация)

Плюсы:

- ноль дополнительных инструментов и абстракций;
- полный контроль над каждым шагом сборки.

Минусы:

- ручная координация порядка сборки зависимостей;
- CI собирает и тестирует всё подряд - медленно и дорого;
- нет встроенного кэширования;
- разные команды для разных стеков, дублирование пайплайнов;
- плохо масштабируется с ростом числа пакетов.

## Последствия

- Все таски проходят через Nx; команды описаны в `package.json` и
  выполняются как `nx affected ...` либо `nx run <project>:<target>`.
- CI должен использовать `affected`-команды и (желательно) общий кэш,
  чтобы получить выигрыш по скорости.
- Каждый новый пакет добавляется как проект Nx со своим `project.json`
  и корректно описанными входами/таргетами.
- Корректность кэша зависит от аккуратного описания `inputs` - это
  зона, за которой нужно следить при изменении структуры проекта.
